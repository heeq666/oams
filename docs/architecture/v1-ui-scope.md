# 第一版界面范围：看板 + 最小后台

日期：2026-10-09
状态：**待开工**。范围与选型已确认，本文定义做哪几页、怎么登录、不做哪些。

配套文档：`v1-hr-department-scope.md`（第一版业务范围）。

## 1. 已确认的两项

| # | 答案 |
|---|---|
| 第一版界面做哪些 | **管理层看板 + 最小后台**。员工自助页延后，先用 MCP 只读工具代查 |
| 前端技术选型 | **服务端渲染（Jinja2）+ HTMX，不引入 Node** |

## 2. 一条容易做反的原则：Web 不是员工填报的主入口

v1 要验证的核心假设是「AI 代笔把填报成本压到接近零」。

**如果先做一个顺手的网页表单，人事专员一定会直接手填。** 填报成本确实降了，但降的不是 AI 带来的，验证就废了。

所以：

- **进度申报的唯一通道是 MCP** 的 `submit_progress`
- Web 侧只做「只读」和「维护」，不提供面向员工的进度填写表单
- 看板**必须显示每条申报的 `submitted_via`**（`human` / `agent`）

这条同时带来一个现成的观测指标：**看板上 human 与 agent 的申报比例**。两周后如果 agent 占比仍是 0，说明 AI 代笔在真实场景里没被接受——比任何问卷都硬。

## 3. 页面清单

### 3.1 看板（P0）

| 路由 | 内容 |
|---|---|
| `GET /board` | 人事部进度看板（第一版只有一个部门，不做部门选择） |

一页之内自上而下：

1. **阻塞项**（`blocked_reason` 非空）——置顶，这是老板最该先看到的
2. **待决策项**（`needs_decision`）——次置顶
3. **工作项列表**——按岗位分组，每项显示：标题、状态、进度值、最近一次申报内容与时间
4. 每条申报旁标注来源：`人工` / `AI 代笔`
5. **负责人显示岗位，不显示人**。工作项挂在 `position_id` 上（v1 硬规则 1），界面上也必须这么呈现，人走了自动跟继任者

### 3.2 最小后台（P0）

| 路由 | 内容 |
|---|---|
| `GET/POST /admin/work-items` | 工作项列表与新建，必须挂 `position_id` |
| `GET/POST /admin/positions` | 岗位与任职维护（复用现有 `/v1/positions`、`/v1/assignments`） |
| `GET /admin/audit` | 审计事件查看（复用现有 `/v1/audit-events`） |

后台不做授权管理页面。第一版只有 4 个用户，授权在初始化时一次性建好，改动走 API/CLI。等用户数涨起来再说。

### 3.3 登录（P0，但形态特殊）

企微 OAuth 仍卡在可信域名，不做员工自助登录（v1 已定）。所以 Web 登录只能复用 CLI 签发的令牌：

- `GET /login` —— 粘贴令牌
- `GET /login?token=<一次性令牌>` —— **首选**，给老板发这个链接，点一下就进去
- 校验通过后：签发 cookie 会话 → **立即 302 到干净 URL**，避免令牌留在地址栏与浏览器历史里

Cookie 要求：`HttpOnly` + `SameSite=Lax`。**不加 `Secure`**——内网是 http，`Secure` 会让 cookie 直接不发送。

### 3.4 明确不做（第一版）

- 员工自助页（查/改/撤自己的申报）——延后到 P1
- 图表（折线、饼图、燃尽）——列表 + 状态标记即可
- 筛选、排序、搜索、拖拽、分页——数据量小到不需要
- 自定义看板布局（v1 已定：由管理员配，不让 AI 搭）
- 敏感字段展示——**第一版看板不显示任何人事敏感字段**（薪资/身份证/合同/绩效），后台脱敏压力因此大幅降低，但审计仍逐条记
- 移动端适配——老板在电脑上看

## 4. 技术形态

### 4.1 目录与依赖

```
app/workhub/
  web.py           # 界面路由（新增），返回 HTML
  api.py           # JSON API（保持现状，MCP 与界面共用）
  templates/       # Jinja2（新增）
  static/vendor/htmx.min.js
```

新增 Python 依赖：`jinja2`。

**HTMX 必须本地打包，不要引 CDN。** 服务器在内网，浏览器很可能取不到公网 CDN，且不该让内部系统的可用性依赖外网。约 40KB，直接进仓库。

### 4.2 部署形态

FastAPI 单进程同时提供 `/v1/*`（JSON）、MCP 与 `/board`、`/admin/*`（HTML）。

**目标机不需要 Node。** 这是选服务端渲染而非 React SPA 的主要理由：Windows 11 Pro 上只装了 Python 和 PostgreSQL，多一条 `npm build` 链路就多一个部署故障点。第一版 4 个用户、1 块看板，SPA 的收益撑不起这个成本。

页面是薄的，换皮不伤数据模型——将来真要扩到全公司、需要复杂交互，再换前端框架不迟。

### 4.3 鉴权要分成两条

现有 `security.py` 的 `current_principal` 从 `Authorization` 头读 bearer token，那是给 MCP 和 curl 用的。界面读不了。

需要新增一个从 cookie 取会话的依赖（例如 `current_principal_web`），**与现有 `current_principal` 共用同一套权限判定与会话表**，只是取令牌的来源不同。

禁止为界面另写一套放行逻辑——否则界面会成为绕过 `require_permission` 的后门。行级过滤、脱敏、审计必须在共用层里，界面拿到的就已经是过滤后的结果。

## 5. 依赖顺序

界面不能先动手，前面还有东西没建：

1. **迁移 0002**（`work_items`、`work_item_reports` + 四个补齐项）——没有表就没有看板
2. **看板聚合接口** ——界面直接消费它，不要在模板里拼 SQL
3. **行级范围过滤**（可粗粒度）+ 敏感字段审计
4. 然后才是 `web.py` 与模板

## 6. 一句话约束

第一版界面只要能做到：**老板打得开、看得出进度和阻塞、看得出这条是人填的还是 AI 填的**，就够了。

前面已经建了一整套底座却没验证过任何真实场景，别在界面上重演一次。
