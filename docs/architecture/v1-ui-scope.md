# 第一版界面范围：看板 + 最小后台

日期：2026-10-09
状态：**待开工**。范围与选型已确认，本文定义做哪几页、怎么登录、不做哪些。

配套文档：`v1-hr-department-scope.md`（第一版业务范围）。

## 1. 已确认的两项

| # | 答案 |
|---|---|
| 第一版界面做哪些 | **管理层看板 + 最小后台**。员工自助页延后，先用 MCP 只读工具代查 |
| 前端技术选型 | **服务端渲染（Jinja2）+ HTMX，不引入 Node** |

## 2. 一条容易做反的原则：Web 不是员工填报的主入口

v1 要验证的核心假设是「AI 代笔把填报成本压到接近零」。

**如果先做一个顺手的网页表单，人事专员一定会直接手填。** 填报成本确实降了，但降的不是 AI 带来的，验证就废了。

所以：

- **进度申报的唯一通道是 MCP** 的 `submit_progress`
- Web 侧只做「只读」和「维护」，不提供面向员工的进度填写表单
- 看板**必须显示每条申报的 `submitted_via`**（`human` / `agent`）

这条同时带来一个现成的观测指标：**看板上 human 与 agent 的申报比例**。两周后如果 agent 占比仍是 0，说明 AI 代笔在真实场景里没被接受——比任何问卷都硬。

## 3. 页面清单

### 3.1 看板（P0）

| 路由 | 内容 |
|---|---|
| `GET /board` | 人事部进度看板（第一版只有一个部门，不做部门选择） |

一页之内自上而下：

1. **指标条**：未完成 / 阻塞 / 待决策 / 从未申报 / 逾期 / 岗位空缺 / AI 代笔占比
2. **图层切换器**：全部 · 阻塞 · 待决策 · AI 代笔 · 沉默（语义见 3.1.1）
3. **流转计数条**：`未开始 N ▸ 进行中 N ▸ 已完成 N`，`↳ 阻塞 N` 作为分支挂在条尾（语义见 3.1.2）
4. **当前图层明细**：完整卡片，含进度值、申报内容、时间、`依据`
5. **负责人显示岗位，不显示人**。工作项挂在 `position_id` 上（v1 硬规则 1），界面上也必须这么呈现，人走了自动跟继任者

**卡片只出现一次。** 流转从来都是一行计数，不是第二份卡片列表——第一版曾把它做成四列看板，
同一张卡在上面是迷你卡、下面是完整卡，两种密度并存，且列按状态切、层按谓词切，两套筛选
逻辑硬叠，逼得断言一半在给"头部计数跟随图层"打补丁。用户一句"不应该是就一个吗"把它打回：
**页面主体是一张列表，流转是它的导航，不是它的复制品。**

#### 3.1.1 图层是过滤，不是第二次聚合

五个图层都是**同一个卡片列表上的谓词**，定义在 `api.BOARD_LAYERS` / `api.layer_matches` /
`api.select_cards`。JSON 接口和页面共用它们，所以徽章上的计数和页面上画出来的卡片必然对得上——
这由 `tests/test_web_ui_e2e.py` 里的三条一致性断言守着（68 项断言全票通过）：

- 图层徽章数 == 列表条数 == `visible_cards` 长度
- 流转条三个可选阶段之和 == 列表条数
- 图层 + 阶段叠加后，页面条数 == `?layer=&stage=` 接口返回的条数

一次只显示一层（用户选定"切换"而非"叠加"）。已知 layer 非法时回退到 `all`，
不渲染成空看板。

#### 3.1.2 流转是一条计数，不是第二块看板

- **「阻塞」不是阶段，是分支**。真实路径是 未开始 → 进行中 → 已完成，阻塞是"进行中
  卡住了"。计数条里用 `↳` 把它挂在主链旁边并标注"分支"，管理层一眼看到堵点，但页面不会
  假装工作会依次流经它。
- **「已完成」只有计数，没有卡片**。`BOARD_QUERY` 只查未完成状态，把它扩到 done 会
  静默改写页面上其他每个数字的语义。出口可见（计数），明细归工作项列表。它在页面上是
  `<span>` 不是 `<a>`：**不可点**，因为点了也只可能回答"这 0 张卡"。断言里明确守着
  `'<a class="stage done' not in html`。
- **阶段筛选是叠加，不是替换**。`?layer=decision&stage=blocked` = 待决策 **且** 阻塞。
  计数条按当前图层计数（所以阶段相加 == 列表），图层徽章按当前阶段计数（所以点哪个标签
  就得到那个数）——两个方向各自忽略自己那一维，在列表里汇合。

真要做「状态之间的流向」（桑基式的 A→B 转移）还需要一张状态变更历史表——现在只有
审计事件里的行快照，不足以还原流转。这张表没建，所以第一版流转只呈现当前分布。

### 3.2 最小后台（P0）

| 路由 | 内容 |
|---|---|
| `GET/POST /admin/work-items` | 工作项列表与新建，必须挂 `position_id` |
| `GET/POST /admin/positions` | 岗位与任职维护（复用现有 `/v1/positions`、`/v1/assignments`） |
| `GET /admin/audit` | 审计事件查看（复用现有 `/v1/audit-events`） |

后台不做授权管理页面。第一版只有 4 个用户，授权在初始化时一次性建好，改动走 API/CLI。等用户数涨起来再说。

### 3.3 登录（P0，但形态特殊）

独立账号中心尚未接入，v1 不做员工自助注册。因此 Web 登录暂时复用 CLI 签发的令牌：

- `GET /login` —— 粘贴令牌
- `GET /login?token=<一次性令牌>` —— **首选**，给老板发这个链接，点一下就进去
- 校验通过后：签发 cookie 会话 → **立即 302 到干净 URL**，避免令牌留在地址栏与浏览器历史里

Cookie 要求：`HttpOnly` + `SameSite=Lax`。**不加 `Secure`**——内网是 http，`Secure` 会让 cookie 直接不发送。

### 3.4 明确不做（第一版）

- 员工自助页（查/改/撤自己的申报）——延后到 P1
- 图表（折线、饼图、燃尽）——列表 + 状态标记即可
- 筛选、排序、搜索、拖拽、分页——数据量小到不需要
- 自定义看板布局（v1 已定：由管理员配，不让 AI 搭）
- 敏感字段展示——**第一版看板不显示任何人事敏感字段**（薪资/身份证/合同/绩效），后台脱敏压力因此大幅降低，但审计仍逐条记
- 移动端适配——老板在电脑上看

## 4. 技术形态

### 4.1 目录与依赖

```
app/workhub/
  web.py           # 界面路由（新增），返回 HTML
  api.py           # JSON API（保持现状，MCP 与界面共用）
  templates/       # Jinja2（新增）
  static/vendor/htmx.min.js
```

新增 Python 依赖：`jinja2`。

**HTMX 必须本地打包，不要引 CDN。** 服务器在内网，浏览器很可能取不到公网 CDN，且不该让内部系统的可用性依赖外网。约 40KB，直接进仓库。

### 4.2 部署形态

FastAPI 单进程同时提供 `/v1/*`（JSON）、MCP 与 `/board`、`/admin/*`（HTML）。

**目标机不需要 Node。** 这是选服务端渲染而非 React SPA 的主要理由：Windows 11 Pro 上只装了 Python 和 PostgreSQL，多一条 `npm build` 链路就多一个部署故障点。第一版 4 个用户、1 块看板，SPA 的收益撑不起这个成本。

页面是薄的，换皮不伤数据模型——将来真要扩到全公司、需要复杂交互，再换前端框架不迟。

### 4.3 鉴权要分成两条

现有 `security.py` 的 `current_principal` 从 `Authorization` 头读 bearer token，那是给 MCP 和 curl 用的。界面读不了。

需要新增一个从 cookie 取会话的依赖（例如 `current_principal_web`），**与现有 `current_principal` 共用同一套权限判定与会话表**，只是取令牌的来源不同。

禁止为界面另写一套放行逻辑——否则界面会成为绕过 `require_permission` 的后门。行级过滤、脱敏、审计必须在共用层里，界面拿到的就已经是过滤后的结果。

## 5. 依赖顺序

界面不能先动手，前面还有东西没建：

1. **迁移 0002**（`work_items`、`work_item_reports` + 四个补齐项）——没有表就没有看板
2. **看板聚合接口** ——界面直接消费它，不要在模板里拼 SQL
3. **行级范围过滤**（可粗粒度）+ 敏感字段审计
4. 然后才是 `web.py` 与模板

## 6. 一句话约束

第一版界面只要能做到：**老板打得开、看得出进度和阻塞、看得出这条是人填的还是 AI 填的**，就够了。

前面已经建了一整套底座却没验证过任何真实场景，别在界面上重演一次。

## 7. 可视化办公室：已决定延后，且已定形

用户提议过"可视化办公室：不同部门不同区域，点击部门放大看内部流转，进度转成图层"。
其中「图层」已在第 3.1.1 节实现；**「办公室外壳」延后到第二个部门进来之后**，理由是
第一版只有 2 个组织单元（1 个真部门），一张平面图点进去就是现在这个看板，空间外壳的
全部成本收不到回报。

但形态已经定死，避免到时候重新讨论：

- **坐标手动配置，反映真实工位** —— 用户明确否掉了"按岗位数自动排网格"。意味着需要
  一份新的配置数据（部门区域坐标 + 工位位置），由管理员在后台维护。
  **代价是要维护；收益是它真的是数字孪生，而不是装饰。** 若图上的位置是编的，它就
  是"看起来像信息、其实不是"的假信息，与项目原则冲突——这是选自动排布会被否掉的原因。
- **录入方式是拖，不是填数字**（2026-10-12 改为可视化编辑）：`/admin/spaces` 在平面图上
  直接拖方块挪位置、拖右下角圆点改大小，不再有 x/y/w/h 输入框。两级画布：楼层（区域，
  绝对坐标）→ 点进部门（工位，**房间内相对坐标**，所以挪动房间不会带着家具跑）。每次
  手势结束 POST 到同一个写接口，**服务端校验与审计一条没少，画布只是视图**；没校准的
  一律虚线，勾"已校准"变实线。支持 Tab + 方向键微调（Shift 迈大步），无 JS 时降级为
  只读 + 删除（表格仍在）。
- **外壳是"套上去"，不是"推倒重来"**。图层与流转先落地、先被真实数据验证，
  第二版把部门卡片换成办公室房间即可。第一版的投入不会作废。
- **两个维度不要混**：办公室是横向空间关系，工作流转是纵向状态变化。房间用来导航，
  点击放大后进去的仍是本章这套"计数条 + 图层 + 一张列表"，不要把流程图塞进平面图里。
