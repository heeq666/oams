# OAMS · 插件宿主概念稿

> 状态：**新方向**（2026-10-22）　·　取代 `docs/architecture/v1-ui-redesign-plan.md`
> 定位一句话：**表面是公司级进度汇报展示网站，实质是一套有权限、有审批的插件宿主。**
> 一切功能以「插件」为单位接入：插件由部门自己写，但必须遵守底座定义的三张契约；审核是插件上架（及每次改版）的闸门。

---

## 0. 三条共识（来自需求方原话，后续所有设计不得违反）

1. **自由在形式，不自由在语义**：部门可以随便决定「报什么字段、怎么排版、首页放哪几个数字」；但只要插件产不出公司汇总需要的标准字段，它就不成立。
2. **插件分两层**：预设模块（平台提供，字段映射已声明）+ 自定义模块（纯容器，只决定排版，叶子必须是预设模块）。
3. **数据主权在部门**：本部门的明细，本部门全体可见；对外只出汇总。

---

## 1. 概念模型：六个名词

| 名词 | 是什么 | 谁拥有 |
|---|---|---|
| **部门插件**（interface） | 一个部门的工作台定义，即 descriptor。有版本，有状态机 | 部门管理员编写，平台审核 |
| **模块**（module） | 页面上的一个积木块。分预设模块与容器两类 | 平台注册表 |
| **容器**（container） | 只能排版的模块。有布局属性，**没有数据、没有文字、没有数据源** | 平台注册表 |
| **字段**（field） | 部门自定义的录入项，必须声明映射到哪个标准字段 | 部门定义 |
| **条目**（entry） | 一条真实的汇报记录，由某人在某插件里填写 | 部门 |
| **标准字段**（canonical field） | 公司汇总用的固定词汇表，全平台只有一套 | 平台 |

关系：**一个插件 = 一组模块 + 一组字段映射 + 一份状态映射 + 一份能力声明**。条目挂在插件上，经由字段映射变成标准字段，标准字段进公司汇总。

## 2. 三张契约（这是整个系统的宪法）

### 契约一 · 字段契约

部门可以起任意字段名（「坑位定稿」「打样中」），但每个字段必须显式声明：

- `type`：text / number / percent / date / enum / link / file
- `map_to`：映射到哪个标准字段；或 `display_only`（只在本部门显示、不进汇总）
- `aggregatable`：能否参与汇总。`display_only` 必须为 false

**标准字段集：直接复用商品数据中心的词汇表**（2026-10-22 实测 3176 款 / 7801 条打样记录 / 245 家供应商 / 7216 个 SKU 库存单元）

不要自己发明一套字段。数据中心已经把公司业务字段基本覆盖了，而且数据每周都在长。标准字段按「对象引用 → 度量 → 时间 → 状态 → 文本证据 → 关系」六类组织：

**A. 对象引用（reference）—— 用数据中心的编码，不自造**

| 标准字段 | 对应数据中心 | 取值 |
|---|---|---|
| `style_code` 款号 | product.style_code | 含新老别名（老编码是历史别名，新旧都可查） |
| `skc_code` / `color` 颜色 | colors | SKC 版本可多版 |
| `sku_code` | skus | 款号+颜色+尺码 |
| `wave` 波次 | product.wave | 88 个已归一值（22A春 … 27A春2、标品） |
| `category` 品类 | product.category | 17 类（背心/衬衫/短裤/短袖/防晒衣/夹克/马甲/毛衣/棉服/配件/裙子/外套/卫衣/腰带/羽绒服/长裤/长袖） |
| `brand` / `designer` / `style_position` | product | 设计师 47 人；style_position 7 个系列 |
| `supplier_code` | suppliers | 245 家，类型：面料商/制衣厂/辅料商/工艺厂 |
| `material_code` | materials | 753 种面料 + 辅料 + 工艺 |
| `order_no` | orders | — |

**B. 度量（measure）—— 必须带单位**

| 标准字段 | 单位 | 来源 |
|---|---|---|
| `count` | 件 / 款 / 个 | 计数 |
| `quantity` | 件 | order quantity |
| `amount` | 元 | paid_amount / spend / sales |
| `percent` | % | progress_value 等 0–100 |
| `ratio` | 倍 | roi |
| `duration` | 天 | 时间差（打样周期等） |

**C. 时间（temporal）**：`planned_at` / `due_at` / `completed_at` / `reported_at`
（数据中心的打样记录已有 6 个时间戳：material_ready / pattern_completed / process_completed / garment_started / sample_completed / selected）

**D. 状态（state）**：`status` + `status_since` 走四态标准映射；业务状态如 `sample_status`（21 态）、`approval_status`（通过/失败/重做/待定/取消）作为**受控枚举**引用，不自由填。

**E. 文本与证据**：`title` / `note` / `evidence_url` / `file`

**F. 关系**：`work_item_id`（挂公司级工作项）、`parent_ref`（父级对象，如款号下的 SKC）

**标准字段 = 数据中心的字段词汇表 + 汇报必需的过程字段（status / progress / note / evidence / needs_decision）。**

这条推翻了原来「12 个自造字段」的方案，好处很直接：部门填的「款号」和商品中心的「款号」是同一个东西，公司汇总可以和业务数据直接对账，不用做映射表。

> 现状缺口仍在：部门填的东西没写 `work_item_id`，公司总览自然是 0。新设计里必须把它变成**显式、可选、且界面上看得见后果**的动作——未关联时界面直接标「本条不进公司汇总」。

### 契约二 · 状态契约

各部门对状态的叫法五花八门（待选品 / 打样中 / 已下单 / 待排产）。插件必须提供 `status_map`，把本部门的词映射到四个标准态：

`planned` → `in_progress` → `blocked`（旁支） → `done`

未映射的状态**不允许存在**。这条保证「公司看板上所有部门的柱子是同一根尺子量的」。

### 契约三 · 汇总契约

插件必须回答：**公司首页那几个数字，分别由我这里的哪个字段、用什么算法算出来。**

- 计数类：`count(where field = value)`
- 求和类：`sum(field)`
- 均值类：`avg(field)`
- 覆盖类：`count(distinct ...)`

每个汇总口径声明一个 `metric_key`，全公司同名口径必须同义。汇总只吃三样东西：`mode='live'`、`status_entry='active'`、`work_item_id IS NOT NULL`。草稿数据与未关联条目**永不进汇总**。

#### 指标目录：预设 + 自定义（两层，不混）

**第一层 · 指标目录（平台拥有）**
所有可上首页的数字，必须在 `metric_catalog` 里注册，有 `metric_key`、口径公式、数据来源、刷新频率。部门插件只能**引用** `metric_key`，不能自己写聚合逻辑。这一层管理员维护，全公司口径唯一。

**第二层 · 首页视图（用户拥有）**
每个用户自己决定首页显示哪些指标、什么顺序、什么范围。**这只是「视图」，改不了口径**——像 Excel 里选哪些列显示，不是改公式。

| 能自定义 | 不能自定义 |
|---|---|
| 显示哪几个指标（从目录里挑） | 指标的计算公式 |
| 排列顺序、卡片大小 | 指标的统计口径 |
| 时间范围（本周/本月/本波次/自定义） | 数据来源 |
| 维度筛选（部门/品类/波次/设计师） | 新增 `metric_key` |
| 保存为个人视图、设默认 | 让指标绕开汇总三条件 |

**为什么这么切**：如果允许用户自定义口径，A 看到的「在研款数」和 B 看到的不是一回事，汇报就没有公共语言了——这正是这个项目要解决的问题。视图自由、口径统一，两者不冲突。

**首批指标目录（第三版）——按「一个款的生命周期」排，删掉资料就绪**

第三版删了资料就绪两项、把「已下单」两格合成一格、首页固定 6 格、波次改为默认当前波次可筛选——对应你刚说的三句话。

**改动一：资料就绪整项删除，不是降级，是不存在。** `funnel.material_ready`（用料快照就绪 3.9%）和 `funnel.fit_ready`（版型资料就绪 4.3%）从指标目录里彻底拿掉。我上一版把数据中心的**质检口径**当成了公司**进度口径**，这是判断错误——它回答的是「资料齐不齐」，公司要问的是「款走到哪、钱回来没有」，两套账不能混。同理 `data.completeness = 36.6%` 也不进首页，理由同一条。

**改动二：「已下单」只看这个款有没有下过单，与回传标记无关。** 原来我把 `ordered`(3) 和 `unmarked_ordered`(26) 拆成两格，是错的。正确口径是 `is_ordered = true` → **29 款**。`order_status` / `order_marked` 只在**详情页做溯源**（能点开看这 29 款里哪几款系统里没标记过），不进首页、也不单独占一格。

**新目录 10 项**，以 26D 冬 1-2 波（68 款）实测：

| # | metric_key | 名称 | 口径 | 26D冬1-2波实测 |
|---|---|---|---|---|
| 1 | `funnel.designed` | 有设计图 | `has_design_image = true` | 59 / 68 |
| 2 | `funnel.sample_done` | 已出样 | 至少一个颜色 `已出样`（款级派生） | 59 |
| 3 | `funnel.sample_wip` | 打样在制 | 无色出样，且有颜色在「在制词表」内（配料中/制版中/工艺中/制衣中/前工艺中/**后工艺**/配料完成/剪裁中/待剪裁/配料完成-待剪裁/**重做/已安排/毛衣已安排**） | 1 |
| 4 | `funnel.sample_pending` | 打样未开始 | 无色出样、无色在制，全部落在「未开始词表」（未开始/未填写/取消/失败/待定/ODM/AI效果图/特殊情况）或无记录 | 6 + 2 |
| 5 | `funnel.priced` | 核价完成 | 该款最新核价版本 = 核价完成 | **13 / 66**（26D冬1-2波，可带波次） |
| 6 | `funnel.ordered` | 已下单 | `is_ordered = true` | **29** |
| 7 | `funnel.not_ordered` | 未下单 | `is_ordered = false` | **39** |
| 8 | `funnel.qty` | 下单件数 | `sum(quantity)` | 63,289 件 |
| 9 | `funnel.gmv` | 下单金额 | `sum(paid_amount)` | ¥1,745.87 万 |
| 10 | `funnel.roi` | 推广 ROI | `sum(marketing_sales) / sum(spend)`，展示**四舍五入**两位 | 6,889,366 / 1,331,248 = 5.1751 → **5.18** |

**打样那三项不是互斥的——但原因和修法跟你可能想的不一样。** `sample_status` 是**颜色**级的：一个款有 4 个颜色，其中 2 个出了样、2 个还没开始，款级字段就把两个状态都列出来，所以 68 款里 11 款挂着多状态。我用 `list_development_records`（按颜色逐条，带 `wave` 过滤且真的生效）核对了这 11 款，确认是**同款不同色**在分别推进，不是脏数据、也不是历史叠加。所以：

- **款级「已出样」= 至少一个颜色出过样** → 59 款。这是首页要看的口径（这个款能不能拍、能不能卖）。
- **颜色级进度**（48 款全色都出样 / 11 款部分出样 / 6 款全未开始 / 1 款在制中）只进部门页，首页不给，否则老板要读四层。
- **不需要写一条「已出样压过一切」的强规则**——那是把颜色级的分布硬压成一个数。写进契约的是另一条更根本的，且已定：**款级打样状态与审批状态只能由颜色级记录派生，部门不得手工填报款级 `sample_status` / `approval_status`**，否则同一款在两个部门那里会有两个答案。落实方式不是删词汇表，而是**禁止字段映射**：`sample_status` / `approval_status` 仍是合法口径名（平台派生数据要用），但 `fields[].map_to` 指向它们会被校验器以 `[DATA_RULE_VIOLATION]` 拒绝，提示改用 `status` 或 `display_only`。见 `descriptor.PLATFORM_DERIVED_FIELDS`。

**首页默认 6 格**（按「一眼看出瓶颈」挑；核价能带波次了，但只有 13/66，进部门页更合适——见下）：

| 格位 | metric_key | 26D冬1-2波 |
|---|---|---|
| 1 | `funnel.sample_done` 已出样 | 59 |
| 2 | `funnel.sample_open` 打样未完成（= 3 + 4，首页用的派生格） | 9 |
| 3 | `funnel.ordered` 已下单 | 29 |
| 4 | `funnel.not_ordered` 未下单 | 39 |
| 5 | `funnel.gmv` 下单金额 | ¥1,745.87 万 |
| 6 | `funnel.roi` 推广 ROI | 5.18 |

第 2 格的 9 款在部门页展开为 在制 1 / 未开始 6 / 未填 2——首页只给总数，不逼老板看三层。

**波次口径：默认当前波次，可筛选。**

- 首页默认 = 当前波次。实现上**不解析波次名称**（`26D冬1-2波` 这种命名随时会变，写死解析规则等于埋雷），用一条配置 `home.default_wave`，管理员在指标目录设置里指定一次；未配置时 fallback 到「最近 30 天有打样或订单活动的波次」。
- 顶栏放波次筛选器，选项直接取数据中心 `filter_options.wave`（实测 88 个，可用），可切任意波次，也可切「全部进行中波次合计」。
- 所以 `funnel.*` 的签名必须带 `wave` 维度参数，默认值来自配置而不是硬编码。

**为什么删到 10 项**：第 1–4 是设计到打样，第 6–7 是下单与否，第 8–10 是钱，第 5 核价单独挂着。任何一段掉档第一屏都能看见，且没有一项是部门台账的搬运。

**两个必须写进实现说明的坑**：

1. **`order_status` 这个筛选参数在 API 上不生效**：`ordered` / `unmarked_ordered` / `not_ordered` 三个值单独传都返回 3,176（等于不过滤）。所以首页不要用它做筛选。但列表项自带布尔字段 `is_ordered`（= 有没有下过单）和 `order_marked`（= 系统里标没标），这两个字段对 26D冬1-2波 给出准确的 29 / 39 切分。**汇总一律基于 `is_ordered`，不用 `order_status`。**
2. **`sample_status` 是数组且历史叠加**，必须按优先级归一后再计数（见上）。这一条不写进契约，各部门插件各算各的，口径立刻就散了。

**关于核价，我上一版说错了，现在纠正**：`list_development_records` 支持 `wave` 过滤，26D冬1-2波 66 个款有开发记录、其中 46 个款有核价记录（59 条记录，一款可多版），款级最新核价状态是 核价完成 13 / 核价中 29 / 取消 3 / 未填写 1。所以核价**拿得到波次口径**，只是数字确实小。

而「核价完成少」你解释得对——**没核价的款本身就是被淘汰的款，这是筛选的结果，不是数据缺失**。所以这个数字的正确读法不是「完成率低、要催」，而是「66 款里 13 款过了核价，说明大部分款在核价环节被砍掉了」。它反映的是**选款严格度**，是个健康信号。

因此核价不进首页 6 格（首页要的是「现在卡在哪」，核价给的是「砍了多少」，节奏不同），但进**部门页的漏斗图**：66 → 出样 59 → 有核价记录 46 → 核价完成 13 → 已下单 29。这条链一画出来，选款严格度自己就说明白了。

> 10 个指标里 9 个不需要任何部门手动填报，直接从数据中心算。只有 `funnel.priced` 的**判定依据**（最新一版核价到底算不算完成）需要和数据中心对齐一次口径——这就是插件宿主真正要解决的事：**数据中心的既有事实 + 部门的过程补充 = 一个完整的进度画面。**

## 3. 模块体系

### 3.1 三层模块

| 层 | 例子 | 有无数据 | 能否进汇总 |
|---|---|---|---|
| **容器** | 行 / 列 / 网格 / 标签页 / 折叠面板 / 分隔线 / 留白 | 无 | 否（自身无数据） |
| **预设·录入模块** | 进度行、明细表、里程碑、阻塞清单、数值录入、证据区 | 有（产生条目） | 视字段映射 |
| **预设·展示模块** | 指标卡、指标网格、流程条、状态分布、排行榜、动态流、说明块 | 有（消费汇总） | 否（只读） |

**铁律：容器里不能直接写字、不能直连数据。任何数值和文字都必须由预设模块产生。**
这条铁律带来一个巨大的好处——**没有可执行代码，所以不需要沙箱**。自定义模块只是布局 DSL，风险面接近于零。

### 3.2 预设模块注册表（建议首批 14 个）

| 模块 | 类型 | 消费标准字段 | 产出 | 可汇总 |
|---|---|---|---|---|
| `progress_row` 进度行 | 录入 | — | status/progress/note/evidence | 是 |
| `table` 明细表 | 录入 | 自定义列 | 多字段 | 是 |
| `timeline` 里程碑 | 录入 | — | due_date/status | 是 |
| `blocker_list` 阻塞清单 | 录入 | — | blocked_reason/needs_decision | 是 |
| `metric_input` 数值录入 | 录入 | — | number 字段 | 是 |
| `evidence_gallery` 证据区 | 录入 | — | evidence | 否 |
| `metric_card` 指标卡 | 展示 | 一个 metric_key | — | — |
| `metric_grid` 指标网格 | 展示 | N 个 metric_key | — | — |
| `flow_strip` 流程条 | 展示 | status 计数 | — | — |
| `status_chart` 状态分布 | 展示 | status 计数 | — | — |
| `rank_list` 排行榜 | 展示 | 排序后的聚合 | — | — |
| `activity_feed` 动态流 | 展示 | reported_at | — | — |
| `note_block` 说明块 | 展示 | — | — | 否 |
| `divider` / `spacer` | 容器 | — | — | — |

### 3.3 容器嵌套上限：**两层**

一层容器定主分区（左指标 / 右明细），二层定局部（一组卡片横排）。三层以上：响应式失控、审核看不懂、出错难定位。超过两层的提交直接在校验阶段拒绝。

### 3.4 模块版本锁定（重要，别漏）

预设模块自己也会升级。所以插件必须**锁定模块版本**：

```yaml
modules:
  - id: metric_card
    version: ^1.2        # 锁定大版本
  - id: progress_row
    version: ^1.0
```

平台发布 `metric_card@2.0` 时：
1. 跑全平台兼容性扫描，列出受影响的插件；
2. 受影响的插件**不受影响地继续跑旧版**（宿主同时装 v1 和 v2）；
3. 部门主动升级 → 走一次审核 → 切到新版。

**绝不允许「平台升级把部门页面搞崩」这种事发生。**

### 3.5 能力声明（「万物皆插件」的真正类比）

插件不是只有布局，它还要**声明自己需要什么权限**，宿主据此授权。审核审的就是这份声明。

```yaml
capabilities:
  - entries:write            # 写本插件条目
  - entries:read:dept        # 读本部门条目明细
  - aggregate:read:dept      # 读本部门汇总
  - aggregate:read:company   # 读全公司汇总（高风险，需二级审批）
  - entries:link:work_item   # 把条目关联到公司级工作项
  - export:dept              # 导出本部门明细（v1 未实现：写了会被拒，见契约 §4）
```

**没有声明 = 没有权限**，不靠前端隐藏，靠后端拒绝。这样「部门做的插件会不会越权看别人数据」这个问题，在架构上就不存在了。

## 4. 版本与审批

### 4.1 版本状态机

```
draft ──提交──▶ pending ──通过──▶ active ──新版本上线──▶ archived
  ▲                │
  └────退回────────┘（附结构化原因）
```

### 4.2 每版必审，但审的是**差异**

- 每次提交 = 一个 `version_no`，不可变；
- 审核页展示 **diff**：新增/删除/修改了哪些模块、字段映射怎么变、能力声明多了什么；
- 审核人通常 30 秒看完，不是重读整页。

### 4.3 线上永不中断

新版 `pending` 期间，`active` 的旧版**照常服务**。只有通过才切换。这条解决「部门一改版就把线上页面改坏」的恐惧，也是部门敢于频繁迭代的前提。

### 4.4 拒绝要可执行

拒绝不是写句「不行」，而是必选原因分类 + 说明：

- `FIELD_UNMAPPED` 有字段没映射到标准字段
- `STATUS_UNMAPPED` 有状态没映射到四态
- `METRIC_UNDEFINED` 汇总口径缺失
- `CAPABILITY_ESCALATION` 申请了超出部门范围的权限
- `MODULE_NOT_WHITELISTED` 用了未注册模块
- `LAYOUT_TOO_DEEP` 容器超过两层
- `DATA_RULE_VIOLATION` 违反数据主权规则（如申请读他部门明细）

部门改完再提交，审核人看到的是「上次那几条是否已修」。

### 4.5 高风险变更需二级审批

只针对三类：① 要对外公开（`meta.visibility: public`）；② 申请 `aggregate:read:company`（这页要进公司汇总数字）；③ 跨部门沿用别部门已上线的页（`based_on` 指向别人的页）。「首次上架」不在这一类里（已定不实现，见下面的引用块）。

> **「首次上架也走二级审批」已定不实现**（2026-11-01 老大拍板）：这条要求每个部门第一次上线也走公司终审，会把所有新页推给平台，属流程变更、收益不值；现有三条判据已经够用。判据实现在 `app/oams/review.py:207` `needs_company_review()`，调用点在 `app/oams/web.py:1424`（部门初审点「通过」那一刻判）。拍板记录与理由见 `p0-interface-contract.md` §4.2。

**二级就是两级节点，点通过即可。**（需求方定：不写意见、不设冷却、不要求不同人）

- 两个审批节点，各自点「通过」或「退回」；
- **不要求写批准意见**，不要求间隔时长，两个人是同一人也行；
- 两次通过都进审计日志（谁、什么时候、批的是哪个版本）——审计是自动的，不额外要人填东西；
- 任何一级点「退回」，都必须写一句原因（这条不省，因为退回是要给对方改的）。

留一个可配置开关，默认全关：`dual_approval.same_reviewer_allowed=true`、`dual_approval.min_interval_minutes=0`。以后若真出过一次乱开权限的事故，把间隔调成 30 分钟即可，**不需要改代码**。

> 说清楚代价：同一人连点两次，本质上就等于一次审批。这是你选的取舍——流程轻、跑得快。它的保险不在审批环节，在**审计日志 + 能力声明的后端强制校验**：越权请求在运行时被拒绝，而不是靠审批时有人看出来。

### 4.6 已知缺口：审核主体未区分平台与部门（下一轮）

评审页 `app/oams/web.py:1041`（队列）、`:1086`（通过）、`:1137`（退回）三处取的都是同一条授权 `workforce.interfaces/review`，`has_permission` 只看 grant 的 effect、不看审核人属于哪个部门；`/reviews` 队列也是全量 `pending`，不按审核主体过滤。也就是说：拿到这条授权的部门管理员，能审自己部门提交的页面。

按本节共识「**部门管理员编写，平台审核**」，缺的不是「部门互斥」，而是**审核主体没分家**——加一条「审核人部门 ≠ 页面部门」的互斥判断反而会把设计意图改歪（平台审核员本来就不属于任何业务部门）。下一轮按「平台审核」建模：把平台审核员与部门管理员区分成不同主体，队列按主体过滤；现在部门侧已经有硬约束：初审要求 `review` 授权、页面在本人部门范围内、且不是自己提交的（`_review_refusal`，`app/oams/web.py:1470`；部门除作者外无人可签时平台代签，审计记为没有部门签字）。口径见 `docs/runbooks/department-page-lifecycle.md`。

## 5. 权限模型：能力 × 范围

### 5.1 两个维度

- **能力**（capability）：能做什么。如 `workforce.reports/submit`
- **范围**（scope）：对谁做。`company` / `org_unit:子树` / `self`

判定顺序：**先能力，再范围，最后行级过滤**。行级过滤必须下沉到数据层（SQL 的 WHERE），不能只靠路由层挡住。

**现状（2026-11-09 按代码与实测写实，取代原先「`effective_grants` 只认 `scope_type='all'`」的说法）：**

- `security.effective_grants`（`app/oams/security.py:383`）**已经支持两档范围**——不传 `org_unit_id` 问「有没有这个权」，传了只算全公司的加正好这个部门的；`company_only=True` 时只认 `scope_type='all'`。所以「只认 all」这句不成立了。
  - **但别把 `scope_type='all'` 读成「全公司范围」**：这套数据里它是**权限标记**。全套种子 67 条授权（`scripts/load_department_data.py` 默认发 all）全部是 `all` 档，一条 `org_unit` 都没有，于是「有 all = 全公司读者」会把每个部门负责人都判成全公司读者（2026-11-09 实测：6 人里 6 人）。判「全公司读者」只能看**座位挂在哪一级部门**（`security.company_seat`，`app/oams/security.py:536`，`unit_type='company'`）；`readable_org_unit_ids`（`app/oams/security.py:561`）就是这么判的。
  - `has_company_scope`（`app/oams/security.py:456`）仍走 `company_only=True`，今天能区分开，只因为 `workforce.grants/manage` 这件事在种子里只发给公司本级岗位——**换个资源就不再成立**，新写「是不是公司级」的判断别抄它的形状，抄 `company_seat`。
- **工作项一族已按它收敛**（6 个端点：`/v1/me`、`/v1/work-items` 读写、`/v1/work-items/{id}/reports` 读、`/v1/board/org-units/{id}`）。
- **管理面没有收敛，而且缺的不是行级 WHERE，是「范围」这个维度本身**：`require_permission`（`security.py:821`）内部调 `has_permission` 不传 `org_unit_id`，等于只问「他有没有这个权」而不问「在哪儿」。结果是**读权 = 全公司读权**。实测（开发库）：只授某部门 `workforce.members/read` 的成员 `GET /v1/members` 返回 200 且含别部门成员。
- **票据范围：已修（2026-11-09，`b7961ad`）**，与上一条是两个轴。原状是 `api.require_app_scope()` 只在 `app/oams/web.py` 12 处调用、`app/oams/api.py` 0 处，只申请 `entries:read:dept` 的票能建部门、建成员、发 company 级授权。修法改成**默认拒绝**：`APP_ROUTE_WHITELIST`（`api.py:2013`）列出票能碰的路由，不在表里的一律 403，新路由默认对票不可见；`tests/test_app_route_whitelist.py` 里有一条穷举闸门守着它。**这条修的是「票」，上面那条修的是「人」，别当成一件事。**

所以重做时要做的是**给管理面引入范围**，不是重写工作项那一半。

### 5.2 数据主权矩阵

| 角色 | 本部门明细 | 本部门汇总 | 他部门明细 | 公司汇总 | 导出 |
|---|---|---|---|---|---|
| 部门成员 | 读 + 写自己条目 | 读 | 否 | 读 | 否 |
| 部门管理员 | 读全部 + 写 | 读 | 否 | 读 | 本部门明细 |
| 审核人 | 读（审核所需） | 读 | 否 | 读 | 审计日志 |
| 公司管理层 | 读 | 读 | 读（只读） | 读 | 全公司 |
| 平台管理员 | 读 | 读 | 读 | 读 | 全量 |

### 5.3 跨部门关联怎么办

工作项可以跨部门（一个公司级项目，生产部供 3 条、运营部供 2 条）。规则：

- 明细归属**写入方部门**，他部门只能看汇总与摘要；
- 需要共享明细时，由数据方主动授予「条目级共享」，不搞隐式可见；
- 这条是后续能力，v1 先不做，但数据结构要预留 `entry_shares` 表位置。

## 6. 数据流

```
部门成员填写
   │
   ▼
[条目 entry] ──字段映射──▶ [标准字段] ──汇总契约──▶ [公司汇总]
   │                          ▲                        │
   │ mode=live                │                        ▼
   │ status_entry=active      │                  [公司看板 / 进度中心]
   │ work_item_id 非空 ────────┘
   │
   └── work_item_id 为空 ──▶ 仅本部门可见，界面上标「不进公司汇总」
```

三个必须做对的细节：

1. **汇总就绪度指示器**：每个条目旁显示一个小标记——已进汇总 / 未关联 / 草稿。让部门自己看得见后果，而不是月底才发现数字是 0。
2. **汇总口径只有一个实现**：`build_board` 这类函数必须唯一，JSON 接口和 HTML 页面都从它渲染，页面永远不可能和接口不一致。
3. **汇总可追溯**：任何一个首页数字，都能点进去看到「由哪几个部门的哪几条条目算出来的」。这是这套系统能不能被信的根本。

## 7. 我认为你还缺的 5 个点（建议补上）

### 7.1 插件模板库
第一个部门做完，第二个部门不想从零写。允许「复制一个已上架插件为草稿」——复制过来的是 descriptor 结构，数据不复制。这会极大加速铺开。

### 7.2 AI 通过 MCP 直接开发插件 + 实时预览（需求方选定，这是正式方案不是建议）

部门管理员**不写 YAML，不点拖拽器**。他的工作方式是：连上 OAMS 的 MCP 服务，用中文跟 AI 说「我们部门想这样汇报」，AI 调 MCP 工具把插件建出来，他在实时预览里看着改。

**MCP 只读通道（AI 了解现状用）**

| 工具 | 作用 |
|---|---|
| `list_modules` | 列出可用模块、版本、参数 schema |
| `list_canonical_fields` | 标准字段词汇表（源自商品数据中心，见契约一） |
| `list_metric_catalog` | 能绑什么指标：`can_bind` 给绑定规则（键形如 `dept.<本单位CODE>.<slug>`、须在本页 `metrics[]` 以 `mode=emit` 声明、聚合限 `count/sum/avg/count_distinct`、展示模块只引本页自己 emit 的键），`metrics` 给目录现状（平台指标已下线，当前为空） |
| `get_plugin` / `list_plugins` | 读现有插件（包括别的部门已上架的，作参考） |
| `preview_descriptor` | **无副作用**：传 descriptor 进去，返回渲染结构 + 校验错误 + 汇总试算 |

**草稿写入通道（AI 改东西用，全部只落到 draft）**

| 工具 | 约束 |
|---|---|
| `create_draft_plugin` | 只能建 `draft`，不可能直接上架 |
| `patch_draft_module` | 按 module_id 改单个模块，不用重写整份 |
| `set_field_mapping` / `set_status_map` | 字段契约与状态契约的专用写入口，写入即跑校验 |
| `submit_for_review` | draft → pending，**唯一能提交上架的入口，且必须人点** |

硬约束（写进 MCP 服务端，不靠 AI 自觉）：
- AI 的 token 只绑定 `plugin:write:draft`，**永远拿不到 `plugin:approve`**——AI 不能自己把插件审批通过；
- 任何写操作强制返回新版本号，AI 无法覆盖已提交的 pending 版本；
- 每次工具调用进审计，标注 `actor=agent` + 会话 id。

**实时预览（这是关键体验，不是附加功能）**
AI 每改一次，页面右侧预览就重渲染一次，用的是**真实模块渲染器 + 假数据**，不是示意图。预览要能切换「部门视角 / 公司汇总视角」，让管理员当场看到「我填的这个字段没映射，所以公司看板上不会出现」。这一条比任何校验错误文案都管用。

**为什么这条路比拖拽器对**：部门管理员的真实能力是「说他想要什么」，不是「会配表单」。AI + MCP 把配置工作吃掉，人只负责判断「长这样对不对」。拖拽器留到以后有非技术用户时再说。

### 7.3 本地校验 CLI
部门管理员是「开发者同事」，但不能要求他们懂平台内部。给两条命令：

```bash
oams plugin check ./my-dept.yaml      # 静态校验：字段映射、状态映射、模块版本、容器深度
oams plugin preview ./my-dept.yaml    # 本地起一个假的渲染预览
```

**校验错误必须指到行号并给修复建议**，不能只说 descriptor 无效。

### 7.4 升级迁移助手
模块大版本升级时，给出「一键生成迁移后的 descriptor 草稿 + 变更说明」，部门点确认再提交。否则模块升级会变成全平台的维护噩梦。

### 7.5 审计即产品
每次审批、每次能力变更、每次数据导出都进审计日志，且**对部门管理员可见**（他看到自己的插件被谁批的、改了什么）。审计不是给合规看的后台，是信任的基础设施。

## 8. 分期落地：第一刀切哪里

**第一刀只做一条竖切，验证整个想法成立**：

> 生产部 · 一个插件 · 三个模块（进度行录入 + 指标卡 + 两栏容器）· 走完 draft→pending→active · 数据进公司看板。

这一条打通，意味着宿主、插件、契约、审批、汇总、展示六件事同时被证明。之后所有扩展都是复制这条路径。

| 阶段 | 内容 | 验收 |
|---|---|---|
| **P0 宿主骨架** | 身份/权限/审计 + 三张契约的校验器 + 模块注册表（先 5 个模块） + **MCP 只读通道（list_* / preview_descriptor）** | `preview_descriptor` 能返回渲染结构与可读错误 |
| **P1 一条竖切** | 生产部插件：进度行 + 指标卡 + 容器 + **MCP 草稿写入 + 实时预览** | 提交→审核→上架→公司看板出现数字 |
| **P2 版本与审批完善** | diff 审核、旧版不中断、结构化拒绝原因、二级审批 | 改版三次不炸线上 |
| **P3 模块库铺开** | 补齐 14 个模块 + 容器嵌套校验 | 第二个部门独立写完自己的插件 |
| **P4 能力声明与模板库** | capabilities 强制校验、插件复制、CLI 预览 | 越权申请被后端拒绝 |
| **P5 AI 与迁移** | AI 经 MCP 建插件 + 实时预览、模块升级迁移助手 | 管理员用中文从零建出一个可上架的插件 |

**明确第一版不做**：跨部门条目共享、对外插件市场、移动端专用布局、真·代码插件（HTML/JS 沙箱）。

## 9. 一个必须先定的岔路口

**「自定义模块 = 纯容器」这个前提，如果在未来某天要变成「允许部门写自己的 HTML/JS」，整个架构的性质就变了**：

| | 纯容器（当前设计） | 真插件 |
|---|---|---|
| 沙箱 | 不需要 | 必须（iframe + CSP + 无网络） |
| 汇总安全 | 天然成立 | 必须契约测试 |
| 审核难度 | 看 diff 即可 | 要看代码 |
| 部门能力要求 | 会写 YAML | 会写前端 |
| 上线速度 | 天 | 周 |

我的建议：**v1 死守纯容器**。真插件留成 v3 的选项，等有部门真的被容器憋住了再说。现在放开，会把「统一标准」这个立身之本丢掉。
