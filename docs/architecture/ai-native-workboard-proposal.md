# AI 原生方向：MCP + Skill 评估

日期：2026-10-09（第二轮，已按用户澄清更正）
状态：**定位仍冻结**。本文不写代码，只定架构与前提。

## 1. 更正：谁提供 agent

第一轮我误以为 Workhub 要自己托管 agent。实际不是：

| 项 | 归属 |
|---|---|
| AI agent（Claude / Cursor / 其他） | **用户自己的**，我们不提供、不托管、不管控模型行为 |
| 我们提供 | **MCP 服务 + Skill 规则文档** |
| 定时数据上报 | **不是我们去抓取**。用户按自己业务需要让 AI 设定时任务，数据由用户侧发起 |
| Skill 的作用 | 在规则里告诉 AI「有定时上报这个能力」，AI 再去告诉用户「你可以这么做」 |

**撤回第一轮的第 6 节结论**——「第一版别做通用 agent，做固定 pipeline」这条判断建立在错误假设上，作废。我们不建 agent 基建，也不建 pipeline。

同时撤回第一轮第 2.2 节的部分表述：「AI 搭看板无人负责」这个批评针对的是我们托管 agent 的情形。用户自带 AI 时，责任人是用户自己，这条批评不成立。

**第一轮中依然成立的部分**：第 2.3 节（预设卡片模块是通用件，别建组件库）和第 3 节（规则层应是组织语义，不是布局）。

## 2. 更正后的定位

**Workhub = 公司组织语义的 MCP 服务。**

- 我们提供**权威的组织事实**：谁在哪个岗位、任期、是否在代理、代理何时到期、谁能看什么
- 用户自己的 AI 通过 MCP 读这些事实，然后按自己的方式工作（搭看板、写周报、推进度）
- Skill 教 AI **怎么用对**这套语义，以及有哪些能力可用

这个定位比"AI 化公司看板"更清晰，也更省钱：

- **无头**：不必自建看板 UI 和渲染层
- **标准化**：MCP 是通行协议，任何支持 MCP 的客户端都能接
- **差异化不变**：飞书/Notion 的 MCP 也能读表格，但它们不知道什么叫岗位、代理、任期。它们不知道张三现在是否在替李四，不知道代理 2026-12-31 到期。**这是我们唯一能给、别人给不了的东西**
- **成本低**：现有 FastAPI 骨架 + 一个 MCP 适配层 + Skill 文档，不必重写业务模型

这不是推翻定位 A（岗位权限中台），是**给 A 换一个面向 AI 的接口层**。

## 3. 架构：软约束与硬约束必须分开

```
Skill 规则文档  ——  软约束，只讲用法与约定
      ↓（AI 读）
用户自己的 AI  ——  我们不提供、不托管
      ↓（AI 调用）
MCP 服务       ——  硬约束：鉴权 + 行级过滤 + 审批队列 + 限流
      ↓
组织语义层     ——  岗位 / 任职 / 权限 / 审计，AI 只读
```

**关键原则：Skill 是提示词，提示词不是执行保证。**

任何安全性要求，写在 Skill 里都等于没有。Skill 可以重复这些规则以改善 AI 行为，但**服务端必须独立强制**。用户换一个不读 Skill 的客户端、或模型忽略提示，安全边界不能塌。

分工：

| 关注点 | 落在哪 |
|---|---|
| 怎么用对、什么时候用哪个工具 | Skill（软） |
| 能不能看、能看多少 | MCP 服务端（硬） |
| 敏感字段是否返回 | MCP 服务端（硬） |
| 能否创建岗位/任职/授权 | MCP 服务端（硬） |
| 定时上报能力是否存在 | Skill 告知 + 服务端提供端点（缺一端都不成立） |

## 4. MCP v1 工具清单（只读优先）

**只读工具（v1 全部）**

| 工具 | 用途 |
|---|---|
| `who_is_responsible_for(position_id)` | 当前谁负责这个岗位，含代理与任期 |
| `list_open_items(position_id)` | 该岗位名下未结工作项 |
| `get_assignment_history(member_id)` | 任职历史，含起止与类型 |
| `check_permission(member, resource, action)` | 授权判定，AI 不得自己推断 |
| `list_org_units()` / `list_positions()` | 组织与岗位目录 |

**草稿工具（v1 可选，绝不直接写）**

- `propose_assignment(...)`
- `propose_permission_grant(...)`

只生成待审草稿，进审批队列，**不落库生效**。

**数据上报**

- `submit_data(target, payload)` —— 供用户侧 AI 按定时任务调用

**v1 明确不提供**：`create_position`、`create_assignment`、`grant_permission`、`update_member` 等任何对权威组织数据的直接写工具。

理由：用户自带 AI 一旦能直接调这些，已确认的业务决策 2（代理双签）和决策 5（例外授权双签）会被一行调用绕过，审计链直接失效。

## 5. Skill 必须写进去的规则

1. **岗位 ID 是稳定的，人不是。** 判断责任用 `position_id`，不要用姓名
2. **任职关系不要缓存。** acting 有 `ends_at`，到期自动失效。每次判定都要重新查
3. **权限判定必须调 `check_permission`，禁止自行推断**
4. **敏感字段（身份证 / 银行卡 / 薪资 / 合同 / 绩效 / 入职材料）永远不要请求**，服务端也不会返回
5. **需要变更岗位、任职、授权时只能提草稿**，告诉用户去走审批，不要尝试直接写
6. **固定数据可以定时上报**：如果用户有周期性业务数据，告知可以用 `submit_data` 配合定时任务，并说明需要先申请一个仅限该目标的令牌

## 6. 更正后新暴露的风险

1. **行级数据范围过滤从「以后再说」变成「第一天必须有」。** 现在只支持 `scope_type='all'`。MCP 一旦开放，调用方是 AI，它会系统性枚举所有数据。缺行级过滤 = 任何员工让自己的 AI 就能拉全公司数据，而且是静默的大规模越权
2. **敏感字段脱敏必须服务端做。** 已列为实现契约的迁移 0002 缺口之一，现在优先级同样上升
3. **限流与结果上限。** AI 会循环翻页。每个工具要有返回条数上限和调用频率限制
4. **Skill 不是执行保证**（见第 3 节）。所有硬约束必须在服务端
5. **「定时上报」需要真实能力兜底。** 只在 Skill 里写一句话是空的——必须有可被调用的 ingest 端点 + 可按目标签发的受限令牌。调度由用户侧 AI 触发，我们只提供接收端

## 7. 意外收获：MCP 路径绕开了企微域名阻塞

企微 OAuth 卡死的原因是 `redirect_uri` 必须落在已备案可信域名下（浏览器跳转，平台强制，无变通）。

**MCP 不需要浏览器跳转。** 它用 bearer token 鉴权：管理员用已有 CLI `issue-token` 签发成员个人令牌，写进客户端配置即可。这条路**不受可信域名约束**。

- 面向 AI 的访问：现在就能做，不需要等域名
- 面向人的网页登录：仍然阻塞，等域名或换身份源

这也意味着首管理员 + CLI 签令牌这条既有路径，正好是 MCP 的天然鉴权方式。

| 迁移 0001（岗位/任职/权限/审计） | **保留，升格为组织语义层**，MCP 的数据来源，AI 只读 |

| 迁移 0002 缺口（主岗唯一性 / 审批记录表 / acting 90 天 CHECK / 字段脱敏） | **全部上升为 MCP 开放前的阻塞项** |
| 行级数据范围过滤 | **开放 MCP 的第一天前置条件** |
| 企业微信 OAuth | 仍阻塞，但**只阻塞网页登录，不阻塞 MCP** |
| 看板 / 呈现层 | **可能整体不需要**。见第 9 节待确认 |
