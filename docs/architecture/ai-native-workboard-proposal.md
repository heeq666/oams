# 公司数字孪生看板：MCP + Skill 方向

日期：2026-10-09（第三轮，含用户四项确认）
状态：**定位仍冻结**。本文不写代码，只定架构、风险与起步顺序。

## 1. 用户已确认的四项

| # | 结论 |
|---|---|
| 1 | **不能无头**。最终目标是公司级看板，管理层看公司在干嘛，相当于**数字孪生**：明的暗的都可视化，进度问题一目了然 |
| 2 | 第一批 MCP 客户端：**WorkBuddy、Codex 等** |
| 3 | 核心场景：把各部门散落在**群聊、口头对话、员工本地电脑**里的工作进度，借助 AI 梳理接入 OAMS |
| 4 | 定时上报不是"用户自己填"，是 **AI 帮用户自动定时上报** |

分工不变：AI agent 是用户自己的，我们提供 **MCP 服务 + Skill 规则文档 + 看板**。

## 2. 判断：方向对，起点错

**第 3 点是真的痛点，而且没有现成工具在做。** 飞书多维表格、Notion、钉钉项目都要求人把结构化数据填进去。它们处理不了"群聊里说了一句'差不多快了'"这种东西。**AI 把非结构化信息梳理成结构化进度，这件事别人做不了，也确实是 AI 时代才成立的。**

配上我们已经有的组织语义层，还有一层别人给不了的价值：AI 梳理出"张三说招聘到 X 了"，我们还能告诉它**张三是招聘专员、现在在代理招聘主管、代理到 2026-12-31 到期**。这是**归属 + 时效性**，是数字孪生能不能态准的关键。

**但起点选错了。** 你要从最不可信的数据源（群聊、口头、本地文件）开始建一个号称"数字孪生"的东西。数字孪生的前提是有可信的事实流，而现在：

- 服务没部署
- 没有任何真实数据
- 没有登录
- 行级过滤没做

**在没有任何事实流的时候谈"数字孪生"，顺序是反的。**（更正：原表述为"用最不可信的源"，既然我们不采集，问题不是源不可信，而是**根本还没有源**。）

## 3. 更正：我们不采集，我们提供填报入口

**上一轮我误以为 OAMS 要去群聊、口头对话、员工本地电脑里抓数据。这是错的，撤回。**

正确理解：

- 群聊、口头对话、本地文件里的进度散落，是**没有好系统可用的症状**，不是我们要接入的数据源
- 我们提供的是一个**好填的系统**。系统好填了，散落自然收敛
- 员工是否让自己的 AI 代填、AI 判断得准不准，**是员工自己的事，责任人是员工**
- 我们要做的是在 Skill 里**告诫 AI 如何正确判断**，剩下的由员工调教他自己的 AI

**由此撤回的两条批评**（原 3.1 监控、原 3.3 个人信息合规）：

| 原批评 | 处置 |
|---|---|
| 3.1 「明暗全可视化 = 监控」 | **大部分撤回**。我们不静默采集，是员工主动申报，监控感不成立 |
| 3.3 授权与个人信息合规 | **大部分撤回**。我们不读本地文件、不读群聊，不存在静默处理 |

**保留的残余风险（降级，但不消失）：**

1. **责任归属解决"出事找谁"，不解决"数据会不会失真"。** 员工对自己的申报负责 ≠ 员工会如实申报。看板一旦被拿来追问和考核，压力会传导为报喜不报忧。这是所有申报系统的通病（周报也一样），**不是我们能靠架构解决的**——但它是真实存在的，管理层要知道看板的这个天性
2. **Skill 告诫不能替代服务端兜底**。见第 4 节

## 3.4 AI 在这个项目里的正确定位

**不是「去散落的地方挖数据」，是「让填报成本趋近于零」。**

- 散落是**结果**，不是原因。原因是没有好填的系统
- 系统本身好填 + AI 代笔 → 填报成本趋近于零 → 散落自然收敛
- AI 是员工的**笔**，不是侦探。责任人是员工，AI 只是帮他写得快、写得规范

这个定位比"AI 挖掘散落信息"健康得多，也现实得多，而且**直接打在"看板死于没人维护"这个真问题上**。

## 4. 强制设计：数据可信度分层

更正后不再需要"L3 不可信源"这一层——我们不采集。模型简化为两类：

| 类 | 来源 | 责任 | 处置 |
|---|---|---|---|
| **系统事实** | API、数据库（如商品中心只读 API） | 系统 | 可直接采信 |
| **人工申报** | 员工自己填，**或员工让自己的 AI 代填** | **员工本人** | 需记录是谁填的、怎么填的 |

**AI 代笔仍属于人工申报，责任人是员工。** 这一点必须在数据模型里体现，不能因为"是 AI 填的"就变成一个无主的数据。

**服务端必须记录的三件事**（Skill 告诫不能替代）：

1. `submitted_by` —— 哪个成员
2. `submitted_via` —— `human` 还是 `agent`
3. **原始依据** —— AI 代笔时它依据了什么，出问题能回溯

以及两条可见性要求：

- **员工能看见"我被上报了什么"，能改、能撤回**
- **管理层能看见这个数是人填的还是 AI 代填的**

理由不是不信任员工，是**出事要能回溯**。Skill 里的告诫能改善 AI 行为，但改善 ≠ 保证（见第 2 轮确立的原则：Skill 是提示词，不是执行保证）。告诫和审计都要有。

## 5. 「AI 自动定时上报」的前提

这个能力成立需要三样东西同时到位，缺一端都是空的：

1. **接收端**：`POST /api/ingest/{target}` 端点 + 可按目标签发的受限令牌
2. **Skill 告知**：规则里写清楚有这个能力、怎么用、谁可以开
3. **调度权在用户侧**：由用户自己的 AI（WorkBuddy / Codex）按其业务需要设定时任务，我们不托管调度器

另外两条约束：

- **上报内容必须员工可见**。AI 替我上报了什么，我要能看到、能改、能否掉
- **AI 总结会失真**。失真数据的责任归属要写清楚，不能变成"AI 说的，不关我事"

## 6. 更正后的遗留说明：接入散落源不再是必做项

既然我们不采集群聊、口头对话、本地文件，原第 6 节的门槛清单**不再是前置条件**。如果将来某部门确实想做，再单独评估，门槛备忘如下：

| 源 | 门槛 |
|---|---|
| 企微群聊 | 会话存档是**付费增值能力**，要求企业已认证，且需向员工明示告知。接入走服务端 SDK，很可能同样受企业可信 IP 约束（**需复核**） |
| 口头对话 | 需要会议转写能力（企微 / 腾讯会议录制转写 API），涉及开通与权限 |
| 员工本地文件 | 需要 agent 在员工机器上执行，且"上报哪些文件、上报什么"必须由员工确认。**静默扫盘是红线** |

## 7. 建议的起步：一个部门的最小闭环

上一轮我说"先接 L1 做一块看板"，现在看范围偏窄——它只验证了"管理层看不看"，没验证"员工填不填"。而后者正是这个方案成立的关键（AI 让填报成本趋零）。

**改成跑一个部门的最小闭环：**

1. **选一个部门**，用它真实的岗位与人员
2. **员工用自己的 AI 填报**（WorkBuddy / Codex 经 MCP 写入），AI 代笔，员工确认
3. **一块管理层看板**，展示这个部门的进度
4. **跑两周**，同时观察两件事：
   - 员工是否**持续**填（验证 AI 是否真把成本压到接近零）
   - 管理层是否真的看、并据此做了决策

两个都成立，方案成立。任何一个不成立，问题就出在它身上，而不是在别处。

**前置阻塞项（在闭环开跑前必须补）：**

- 行级数据范围过滤
- 敏感字段脱敏
- 迁移 0002 的四个缺口（主岗唯一性 / 审批记录表 / acting 90 天 CHECK / 字段脱敏）
- MCP v1 只读 + 写走审批

这些可以并行做，但**没做完就别开 MCP 给员工用**。

## 8. 与既有资产的关系

| 既有资产 | 处置 |
|---|---|
| 迁移 0001（岗位/任职/权限/审计） | 保留，升格为组织语义层，是申报数据能做**归属**的唯一依据（谁填的、他是哪个岗位、是否在代理） |
| FastAPI 服务骨架 | 保留，新增 MCP 适配层、申报写入端点、看板渲染 |

| 行级过滤 + 字段脱敏 | **开放 MCP 前的阻塞项**，且看板面向管理层后同样是硬要求（决策 3：管理层只看部门级汇总） |
| PAT 鉴权作为试用期临时方案 | 维持。面向 AI 的访问当前可用；面向人的网页登录后续接入独立账号中心 |
| 决策 3（HR 独占字段 / 管理层只看汇总） | **与"数字孪生"直接冲突**。"明的暗的都可视化"如果包含个人明细，就违反已确认的决策 3。**必须先澄清管理层到底能看到多细** |
