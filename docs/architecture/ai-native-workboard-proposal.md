# 公司数字孪生看板：MCP + Skill 方向

日期：2026-10-09（第三轮，含用户四项确认）
状态：**定位仍冻结**。本文不写代码，只定架构、风险与起步顺序。

## 1. 用户已确认的四项

| # | 结论 |
|---|---|
| 1 | **不能无头**。最终目标是公司级看板，管理层看公司在干嘛，相当于**数字孪生**：明的暗的都可视化，进度问题一目了然 |
| 2 | 第一批 MCP 客户端：**WorkBuddy、Codex 等** |
| 3 | 核心场景：把各部门散落在**群聊、口头对话、员工本地电脑**里的工作进度，借助 AI 梳理接入 Workhub |
| 4 | 定时上报不是"用户自己填"，是 **AI 帮用户自动定时上报** |

分工不变：AI agent 是用户自己的，我们提供 **MCP 服务 + Skill 规则文档 + 看板**。

## 2. 判断：方向对，起点错

**第 3 点是真的痛点，而且没有现成工具在做。** 飞书多维表格、Notion、钉钉项目都要求人把结构化数据填进去。它们处理不了"群聊里说了一句'差不多快了'"这种东西。**AI 把非结构化信息梳理成结构化进度，这件事别人做不了，也确实是 AI 时代才成立的。**

配上我们已经有的组织语义层，还有一层别人给不了的价值：AI 梳理出"张三说招聘到 X 了"，我们还能告诉它**张三是招聘专员、现在在代理招聘主管、代理到 2026-12-31 到期**。这是**归属 + 时效性**，是数字孪生能不能态准的关键。

**但起点选错了。** 你要从最不可信的数据源（群聊、口头、本地文件）开始建一个号称"数字孪生"的东西。数字孪生的前提是有可信的事实流，而现在：

- 服务没部署
- 没有任何真实数据
- 没有登录
- 行级过滤没做

**用最不可信的源建数字孪生，顺序反了。**

## 3. 最大风险：这不是技术问题，是信任问题

### 3.1 「明的暗的都可视化」在员工视角就是监控

把员工本地电脑里的内容、群聊里的口头对话，吸进来给管理层看。员工一旦意识到，会做两件事：

1. **不配合** —— 把真正的工作挪到系统外
2. **报假数据** —— 专门喂给看板看的内容

结果就是：**看板很漂亮，数据是垃圾。**

**数字孪生最大的失败模式不是"孪生不精确"，是"孪生得很精确，但孪生的是员工想让你看到的东西"。** 度量一旦变成目标，就不再是好度量。

这不是可以后期修补的问题，它决定第一版的设计。

### 3.2 不可信源被结构化之后更危险

群聊和口头对话本身就是不可信的：吹牛、含糊、"快了""差不多""在推进"。

AI 梳理之后，这些变成了一个进度条上的 80%。**危险在于它给垃圾数据套上了权威外壳。**

- 没有数据时，管理层知道自己不知道
- 有假数据时，管理层以为自己知道，并据此决策

**后者比前者糟得多。**

### 3.3 授权与合规

AI 读员工本地文件、群聊记录并自动上报，涉及个人信息处理。必须满足：

- 明确授权，明确范围
- 员工能看见"我被上报了什么"
- 可撤回、可更正
- 保留 AI 原始依据，出问题时能回溯

具体条款需按《个人信息保护法》确认，不在本文结论内，但**上线前必须有答案**。

## 4. 强制设计：数据可信度分层

**每一个数据点必须带 provenance（来源）和置信度，看板必须能区分三层，不允许混在一起显示。**

| 层 | 来源 | 可信度 | 处置 |
|---|---|---|---|
| **L1** | 系统 API、数据库 | 高 | 可直接采信。**从这里起步** |
| **L2** | 人工填报 | 中 | 依赖人维护，是看板最常见的死因 |
| **L3** | AI 从群聊 / 口头 / 本地文件推断 | 低 | 必须标注来源、置信度、时间 |

L3 数据在 UI 上必须有**视觉区分**（不同标记 / 颜色 / 悬浮显示依据），且必须能一键看到 AI 的原始依据原文。

**混淆三层 = 系统失去信任 = 项目死。** 这不是nice-to-have，是硬性设计约束。

## 5. 「AI 自动定时上报」的前提

这个能力成立需要三样东西同时到位，缺一端都是空的：

1. **接收端**：`POST /api/ingest/{target}` 端点 + 可按目标签发的受限令牌
2. **Skill 告知**：规则里写清楚有这个能力、怎么用、谁可以开
3. **调度权在用户侧**：由用户自己的 AI（WorkBuddy / Codex）按其业务需要设定时任务，我们不托管调度器

另外两条约束：

- **上报内容必须员工可见**。AI 替我上报了什么，我要能看到、能改、能否掉
- **AI 总结会失真**。失真数据的责任归属要写清楚，不能变成"AI 说的，不关我事"

## 6. 数据源的现实门槛（需逐项核实）

别把这三件事想成"接个 API 就行"：

| 源 | 门槛 |
|---|---|
| 企微群聊 | 会话存档是**付费增值能力**，要求企业已认证，且需向员工明示告知。接入走服务端 SDK，很可能同样受企业可信 IP 约束（**需复核**） |
| 口头对话 | 需要会议转写能力（企微 / 腾讯会议录制转写 API），涉及开通与权限 |
| 员工本地文件 | 需要 agent 在员工机器上执行（WorkBuddy 本地 agent 可以）。但"上报哪些文件、上报什么"必须由员工确认，不能后台静默扫盘 |

**静默扫描员工电脑是红线。** 技术上能做，做了就别指望员工信任这个系统。

## 7. 建议的起步顺序

**先做 L1，不要先做 L3。**

1. **接一个已有的、结构化的、可信的数据源**，做成一块真看板，给管理层真看
   - 现成候选：商品中心的只读 API（既定边界内，不直连其库）
   - 这一步验证的是：**管理层真的会看吗、看了会改决策吗**
2. **补阻塞项**：行级数据范围过滤、敏感字段脱敏、迁移 0002 的四个缺口
3. **开 MCP（v1 只读）**，让 WorkBuddy / Codex 先接进来，跑通组织语义查询
4. **再加 L3**：AI 梳理非结构化源，作为**补充**，带来源与置信度标注
5. 最后才谈"明的暗的都可视化"

第 1 步如果管理层不看，后面四步都不用做。**验证成本最低的一步必须先做。**

## 8. 与既有资产的关系

| 既有资产 | 处置 |
|---|---|
| 迁移 0001（岗位/任职/权限/审计） | 保留，升格为组织语义层，是 L3 数据能做**归属**的唯一依据 |
| FastAPI 服务骨架 | 保留，新增 MCP 适配层、ingest 端点、看板渲染 |
| MCP v1 只读 + `propose_*` 草稿进审批 | 维持。**禁提供 create_position / create_assignment / grant_permission 等直接写工具**，否则决策 2、5 的双签被一行调用绕过 |
| 行级过滤 + 字段脱敏 | **开放 MCP 前的阻塞项**，且看板面向管理层后同样是硬要求（决策 3：管理层只看部门级汇总） |
| PAT 鉴权绕开企微域名阻塞 | 维持。面向 AI 的访问现在就能做；面向人的网页登录仍等域名 |
| 决策 3（HR 独占字段 / 管理层只看汇总） | **与"数字孪生"直接冲突**。"明的暗的都可视化"如果包含个人明细，就违反已确认的决策 3。**必须先澄清管理层到底能看到多细** |

## 9. 待确认（按顺序，前一个没答案就别推进后一个）

1. **管理层能看到多细？** "数字孪生"和已确认的决策 3（只看部门级汇总、不看个人明细）冲突。管理层能看到个人层级的进度吗？能看的话，决策 3 要改
2. **第一个 L1 数据源是什么？** 商品中心 API 可以吗？还是另有其物
3. **谁先看第一块看板？** 具体的人。不是"管理层"这个抽象概念
4. **员工知情与授权怎么走？** L3 上线前的合规前提
5. 企微会话存档是否已开通、是否付费（决定群聊这条源能不能做）
