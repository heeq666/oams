# 全公司工作进度系统：身份、岗位与权限底座方案

> 状态：方案草案。用于人事招聘试点前评审；当前不创建正式账号、不调整生产权限。登录认证后续接入独立账号中心。

## 1. 目标与设计原则

先解决“谁在什么岗位、岗位负责什么、能看和能改什么”，再让部门 AI 助手采集工作内容并接入公司进度系统。工作进度数据必须归属于稳定的岗位/工作项身份，不能只挂在某个员工姓名下。

1. 独立账号中心负责登录认证、稳定账号主体和账号状态；主系统负责岗位、工作配置、业务授权和审计。
2. 员工身份、岗位身份、任职关系、岗位职责配置分别建模，人员变化不重建岗位。
3. 岗位配置采用版本化；生效中的配置不被静默覆盖，历史记录可还原。
4. 同岗换人继承岗位当前有效工作和权限；调岗按新岗位授权，旧岗位权限按任职结束时间回收。
5. 借鉴配置是复制出新版本/新岗位配置，之后互不联动。
6. 默认最小授权。账号中心的组织属性或职位文字不能直接等价为业务权限。

## 2. 核心实体

| 实体 | 稳定标识 | 用途 |
|---|---|---|
| 员工 `workforce_members` | 内部 `member_id`；外部映射保存账号中心的租户 ID + 主体 ID | 记录身份状态及账号中心映射；离职员工停用，不删除历史 |
| 组织单元 `org_units` | 内部 ID；可映射账号中心或组织目录的外部 ID | 记录部门/团队及其历史关系 |
| 岗位 `positions` | `position_id` | 稳定岗位身份；例如“招聘负责人”，不因人员变更而更换 ID |
| 任职 `position_assignments` | `assignment_id` | 员工在岗位上的任期，含生效/结束时间、主岗/兼岗/代理类型 |
| 岗位配置版本 `position_config_versions` | `config_version_id` | 岗位职责、工作项模板、状态规则、更新频率及字段定义的不可变版本 |
| 权限策略 `permission_grants` | `grant_id` | 角色/动作/数据范围及授权来源、有效期；支持岗位默认授权和有期限的个人例外 |
| 工作项 `work_items` | `work_item_id` | 招聘岗位需求或其他管理事项；关联责任岗位、当前负责人和配置版本 |
| 审计事件 `workforce_audit_events` | `event_id` | 记录登录映射、任职、配置、授权、撤权及工作移交变更 |

工作项负责人可作为当前任职员工的展示投影，但责任关系应指向 `position_id`。历史负责人从任职时间和变更审计中还原，不能在换人时覆盖掉。

## 3. 人员变动规则

| 场景 | 系统动作 | 历史与权限 |
|---|---|---|
| 同一岗位换人 | 结束旧任职，新增新员工任职；岗位 ID 和当前岗位配置不变 | 工作项继续归属岗位；旧员工个人会话和岗位授权失效；新任职生效后获得岗位授权 |
| 员工调岗 | 结束旧岗位任职，新增目标岗位任职 | 新权限由新岗位策略计算；不能把旧岗位的额外授权一并带过去 |
| 一人兼岗 | 每个岗位单独建立有效任职 | 权限取多个有效任职授权的合并结果；高敏感动作仍可要求单独审批 |
| 临时代理 | 建立有起止日期的代理任职或代理授权 | 到期自动失效；原岗位负责人及代理关系均留审计记录 |
| 新增岗位 | 新建岗位并建立初始配置版本 | 可从模板岗位复制职责/字段/流程；新岗位 ID、权限和数据范围独立 |
| 职责调整 | 基于当前配置创建下一版本，指定生效时间和审批人 | 已有工作项保留原配置版本快照；明确选择是否迁移到新版本 |
| 岗位停用/拆分/合并 | 停止新分配，按审批的迁移方案转移未结工作项 | 不删除旧岗位、旧配置或审计历史；迁移前后关系可查询 |
| 离职 | 撤销有效任职、会话和个人授权 | 工作项进入交接队列或按规则交给岗位继任者；保留历史，不保留登录权 |

同岗换人的默认原则是“继承岗位当前工作，不继承前任个人额外权限”。例如前任临时获准查看薪资明细，不自动授予继任者。

## 4. 独立账号中心与主系统授权

登录认证后续统一由独立账号中心提供。典型流程：

1. 用户从账号中心登录，账号中心完成凭据校验和必要的多因素认证。
2. Workhub 校验账号中心签发的授权码或令牌，并取得稳定的租户 ID 与主体 ID。
3. 用租户 ID 与主体 ID 匹配内部员工记录；未知主体进入待绑定状态，不自动创建岗位或权限。
4. 查询当前有效任职、岗位配置版本及权限策略，建立 Workhub 会话。
5. 每次受保护请求都由服务端校验会话、岗位授权和数据范围；前端隐藏菜单仅用于界面体验，不是安全边界。
6. 账号停用、离职、调岗、代理到期或手动撤权时，撤销 Workhub 会话或递增令牌版本，并让后续请求重新计算权限。

账号中心可以提供显示名称、账号状态或组织属性作为身份匹配线索，但岗位分配、工作数据范围和写权限必须经过 Workhub 确认。Workhub 只获取完成身份匹配所需的最小字段，不把敏感个人资料作为默认依赖。

### 接入前核对

- 账号中心采用的认证协议、授权码/令牌校验方式和签名密钥轮换机制。
- 稳定租户 ID、主体 ID、显示名称和账号状态字段的定义。
- 未知主体绑定、重复映射、账号合并和解绑的处理规则。
- 账号停用与恢复事件如何同步，以及 Workhub 会话的最长失效延迟。
- 回调地址、HTTPS、测试账号、账号中心负责人和回滚联系人。

账号中心接口尚未在本仓库实现；接入时应根据其正式契约编写适配层，不能根据临时字段名称推断身份语义。

## 5. 主系统当前能力与差距

仓库已有业务角色与外部身份映射的方向性设计。当前本地商品数据中心的 API 主要使用单一 `PREVIEW_ACCESS_KEY` 做服务级 Bearer 鉴权；这适合服务间调用，不等同于员工个人登录，也没有岗位级数据行授权。

现有 `rhythm_task_plans` 是商品节奏工作台的计划覆盖层，`plan_owner` 目前是文本字段，不能直接充当全公司员工、岗位任职或权限底座。因此本项目若承载公司工作进度，应新增独立的人员/岗位域和工作项域，商品模块按需关联，不应复用商品 ID 作为通用事项主键。

首期落地前需要补齐：

- 独立账号中心适配层、员工绑定、会话签发/续期/撤销。
- 员工、组织、岗位、任职历史、配置版本和授权审计的数据模型。
- 后端统一授权中间件；当前 API Key 继续只用于受信任的系统间集成，不暴露给浏览器作为个人身份凭据。
- 部门/岗位管理界面或受控管理入口，含任职审批、配置变更审批、交接和撤权。
- 行级数据范围策略与查询层强制过滤。

## 6. 权限模型建议

权限按 `主体 + 资源 + 动作 + 数据范围 + 有效期` 表达：

- 主体：有效岗位、临时代理关系；个人例外必须有原因、审批人和过期时间。
- 资源：人员/组织、岗位配置、工作项、部门汇总、敏感字段。
- 动作：查看、创建、编辑、分配、审批、导出、管理授权。
- 数据范围：本人负责的岗位、所属部门、指定跨部门项目、全公司汇总。
- 生效信息：来源任职/审批单、开始时间、结束时间、撤销时间。

初始角色可先控制在：系统管理员、部门负责人、岗位负责人、普通成员、管理层只读。角色只说明可做什么，具体能看哪些记录由数据范围决定。薪资、候选人联系方式、面试评价等人事敏感数据单独授权；管理驾驶舱尽量只展示岗位级汇总和风险。

## 7. 人事招聘试点验收

选用真实但已脱敏的招聘需求表，按以下案例验收身份和岗位生命周期：

1. 招聘负责人 A 登录后只看到获授权的部门岗位和招聘进度。
2. 同岗由 A 换为 B，招聘需求、进度历史和岗位配置延续；A 失去访问，B 获得岗位权限。
3. A 调任其他岗位后不再因旧任职看到招聘数据；其新岗位权限独立生效。
4. 新增“招聘运营”岗位，从“招聘专员”复制配置后修改，两个岗位后续变更互不影响。
5. 代理授权到期后自动收回；离职成员无法继续访问，未结工作项可交接。
6. 账号中心未绑定主体、已停用账号、重复映射、无有效任职的登录都有明确拒绝或待处理结果。
7. 配置版本、任职、授权和移交动作都能查看操作者、审批人、时间和变更前后值。

## 8. 推荐实施阶段

### 阶段 A：业务规则确认

由人事/行政、账号中心负责人和系统负责人确认账号主体映射、岗位目录来源、岗位负责人机制、一人多岗、代理、调岗、离职交接、配置审批人及敏感数据分级；暂不开始自动写入。

### 阶段 B：身份与岗位底座

先用账号中心测试租户完成登录身份匹配；建立人员、岗位、任职、配置版本、授权和审计模型；以小范围测试账号跑完上述换岗案例。

### 阶段 C：招聘数据接入

在身份授权通过后，让人事负责人提供脱敏样表。AI 只生成字段映射、状态映射和缺项报告；负责人确认后导入岗位工作项，保存来源、更新时间和配置版本。

### 阶段 D：管理看板与 Skill

基于经试点验证的数据规则构建看板；Skill 帮助部门 AI 理解岗位配置、分析本地表格和生成待确认数据。Skill 不保存企业密钥、不自行授予权限、不绕过主系统授权 API。

## 9. 评审时需要做出的决定

1. 主系统中岗位目录的权威维护者：人事维护，还是由组织目录同步后在主系统确认？
2. 同一岗位可以有几名正式任职者；岗位是否要求指定一个主负责人？
3. 兼职和代理场景由谁批准、最长有效期如何设定？
4. 同岗换人时哪些开放事项自动交接，哪些需原负责人/主管确认？
5. 哪些人事字段属于仅 HR 可见；管理层看板允许展示到什么粒度？
6. 账号中心测试租户、认证契约、回调地址及服务器出口由谁负责？

## 10. 账号中心接入参考

账号中心尚未选定或接入。本节保留为后续适配层的契约检查清单，不绑定任何具体身份平台：认证协议、令牌校验、稳定主体 ID、账号状态同步、密钥轮换和回调安全。

以上为技术方案参考；真正实施前按企业当前应用类型与后台权限复核官方文档和实际返回值。
