# 身份、岗位与权限底座：首期实现契约

状态：首版服务代码与数据库迁移已实现，尚未部署到服务器或连接真实数据库。企业微信接入仍未开始。迁移只适用于 Company Workhub 专用 PostgreSQL 数据库。

## 1. 已实现的代码

- `app/workhub/api.py`：FastAPI health、个人信息、组织单元、员工、岗位、任职、配置版本、授权和审计 API。
- `app/workhub/security.py`：数据库会话令牌哈希校验、过期/撤销和令牌版本检查；服务端授权检查拒绝任何未匹配的主体/资源/动作。
- `app/workhub/cli.py`：迁移、一次性首管理员引导、受控运维令牌签发和 API 服务命令。SQL 迁移作为 Python 包数据随发布包分发。
- `db/migrations/0001_workforce_identity_position_permission.sql`：专用 Workhub schema 的首个迁移。

首管理员从可信运维 shell 建立，OAuth 未接入前不允许伪造企业微信登录。当前管理 API 仅通过 `scope_type = 'all'` 授权；`org_unit`、`selected_positions` 等范围尚未接入请求级行过滤，不能把这些策略当成已经生效。

## 2. 数据模型

迁移 `db/migrations/0001_workforce_identity_position_permission.sql` 建立 `workhub` schema，包含：

- `workforce_members`：内部稳定员工 ID、雇佣状态和会话版本号。离职时停用并递增 `token_version`，不删除员工。
- `member_external_identities`：外部登录主体映射，唯一键为提供方、租户和主体 ID。企业微信 `userid` 应连同 `corp_id` 保存为 `tenant_id + subject_id`；只允许一个有效映射自然键，解绑采用撤销标记并保留历史。
- `org_units` / `org_unit_external_refs`：内部组织目录及企微部门映射。外部同步仅提供建议数据，不据此授予业务权限。
- `positions`：稳定岗位身份，组织变化或换人不改变岗位 ID。
- `position_assignments`：成员与岗位的有始有终任职；代理必须有截止时间。数据库排斥约束禁止同一成员对同一岗位存在重叠有效任期。
- `position_config_versions`：岗位职责/工作流 JSON 配置的版本记录。有效窗口不可重叠；服务层必须禁止更新已审批或已生效版本，变更通过插入下一版本完成。
- `permission_grants`：岗位默认授权和限期个人例外。个人授权必须设截止时间，且记录原因、创建者、审批者和来源任职；授权作用域显式表达。
- `workforce_sessions`：仅存令牌摘要，校验员工状态、令牌版本、过期和撤销状态。
- `workforce_audit_events`：记录身份、任职、配置、授权、会话和交接事件的前后状态。

## 3. 服务端授权判定

所有个人请求必须由后端识别会话并执行授权；前端隐藏菜单不构成访问控制。授权查询至少按以下顺序执行：

1. 校验令牌摘要、过期/撤销状态、成员 `employment_status = active` 和会话 `token_version = workforce_members.token_version`。
2. 读取请求时刻有效的任职：`status IN (active, scheduled) AND starts_at <= now() AND (ends_at IS NULL OR now() < ends_at)`。保留 `scheduled` 状态可让未来任职无需定时任务也能按生效时间自然启用；代理任职自然在截止时失效。
3. 汇总这些任职对应的岗位授权和有效个人例外。匹配资源、动作、作用域与请求目标；拒绝规则优先于允许规则。无匹配授权一律拒绝。
4. 执行数据范围过滤后才读取或修改业务记录。范围计算也必须在服务端完成，不能信任请求传入的组织/岗位范围。
5. 对授权变更、敏感数据访问、管理操作写审计记录。审计写入与业务变更放在同一数据库事务中。

工作项（后续阶段建表）应以 `position_id` 表达责任岗位，并把创建时的 `config_version_id` 固定为快照引用。负责人姓名是当前任职的展示投影，不应作为唯一责任键。

## 4. 生命周期写入规则

- **同岗换人**：一个事务内结束前任任职并撤销其关联会话/个人例外，新增继任者任职；岗位和工作项不变。继任者仅从岗位授权获得权限。
- **调岗**：结束原任职，新增目标任职，递增会话版本使旧授权缓存失效；不得复制旧岗位的个人例外。
- **兼岗**：各岗位分别建任职；权限取有效岗位授权并集，拒绝规则优先。
- **代理**：建 `assignment_type = acting` 的限期任职并要求审批；到期后授权查询立即失效，不依赖定时任务才能拒绝请求。
- **配置修改**：从上一版本复制为新草稿，审批后设置生效时间；严禁静默改写历史 JSON。岗位模板复制只拷贝配置内容，不复用配置版本 ID 或权限主体。
- **离职/停用**：将成员标为 departed/suspended，递增会话版本，撤销会话和个人授权、结束任职；保留身份映射和审计历史，未结工作项进入交接流程。

## 5. 本迁移的边界

当前 DDL 建立身份与权限底座；CLI 可在专用数据库中引导第一个管理员，但不创建真实员工或企业微信应用。它不包含招聘工作项表、OAuth 回调、审批 UI、RLS 策略或商品中心 API 客户端。商品中心仍通过独立只读 API 接入，不复用其数据库账号或表。

部署前需在专用数据库验证迁移，并按服务运行账号拆分 schema 所有者和运行时权限；运行时账号不应有 DDL、删除历史记录或绕过审计的权限。数据库备份、恢复演练、内网端口和 TLS/代理策略属于 Windows 服务器部署阶段。

## 6. 业务决策待确认

以下决定会影响权限策略或管理流程，当前不以技术默认代替业务决定：

1. 正式岗位是否允许多人同时任职；主岗唯一性如何定义。
2. 代理的批准角色和最长有效期。
3. 哪些人事字段仅 HR 可见，管理层汇总允许展示的粒度。
4. 任职结束时开放工作项自动转交岗位继任者，还是进入主管确认队列。
5. 岗位目录权威维护者，以及配置版本和个人例外授权的审批角色。

## 6. 迁移前提与验证

迁移要求 PostgreSQL 中可安装 `pgcrypto` 和 `btree_gist` 扩展；扩展安装权限应由数据库管理员预先授予或由迁移管理员执行。扩展显式安装在 `workhub` schema。`workhub` schema 只是专用数据库内部的命名空间，不能替代 README 所要求的独立数据库、专用账号、独立备份和网络隔离。

已确认可通过本机 SSH 配置的 `win` 别名只读连接到 Windows 服务器；PostgreSQL 16 服务正在运行，数据目录为 `D:\pgdata`，`postgres.exe` 在 `0.0.0.0:5433` 监听且本机 TCP 探测成功。未检查或读取凭据，也未查询数据库内容；本工作区没有 `psql` 客户端或目标数据库连接参数，因此未执行真实迁移。部署前需在目标 PostgreSQL 版本的空白专用数据库执行并做回滚/重放验证；如目标版本不支持扩展安装到指定 schema，应由 DBA 调整扩展策略并确认运行时账号权限。
