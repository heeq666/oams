# 第一版范围：人事部门进度闭环

日期：2026-10-09
状态：**待开工**。三个前置问题已回答，本文定义第一版做什么、不做什么、怎么验收。

## 1. 已确认的三项

| # | 答案 |
|---|---|
| 管理层能看到多细 | **啥都能看**，包括个人层级明细 |
| 第一个跑闭环的部门 | **人事部门** |
| 谁看第一块看板 | **老板、管理员、人事经理、人事专员** |

### 由此作废的决策 3

实现契约第 6 节原决策 3 为「管理层只能看部门级汇总，不得查看个人明细」。**已作废**，改为：

- 管理层可看个人层级的工作进度明细
- **人事敏感字段不随"管理层"自动放开**：身份证、银行卡、薪资、合同、绩效、入职材料仍需单独授权
- **「管理层」不是一个可见粒度**，必须展开为角色 → 范围矩阵

最小矩阵（第一版）：

| 角色 | 可见范围 | 敏感字段 |
|---|---|---|
| 老板 | 公司级全部 | 需单独确认能否看薪资 / 绩效 / 身份证 |
| 管理员 | 公司级全部（技术角色） | **不应看敏感字段**，管理员是运维不是业务角色 |
| 人事经理 | 人事部 + 本人 | 可看（HR 岗位） |
| 人事专员 | 人事部 + 本人 | 按岗位授权范围，未必等同经理 |

**管理员能看全部 ≠ 管理员该看薪资。** 这条要在实现时分开，别用"管理员最大"一把梭。

敏感字段访问**逐条记审计**：谁、什么时间、看了谁的哪个字段。

## 2. 开工前必须先讲的两件事

### 2.1 迁移 0001 里没有任何工作项

现有表：成员、外部身份映射、组织、岗位、任职、配置版本、授权、会话、审计。

**没有工作项、没有申报记录、没有看板。** 整个"看板"这一侧一行代码都没有，第一版要新建。

### 2.2 选人事部门做第一个部门，有样本偏差

人事部门是这套系统的推动者，人少（经理 + 专员）、离项目近、有动力配合。**他们会填。**

**所以人事部门跑通，只能证明链路是通的，不能证明方案成立。** 真正要验证的是那些散落最严重的部门（业务、运营、技术）会不会持续填。

把这个当成阶段一，别当成结论。人事跑通之后，**必须尽快接一个"难啃"的部门**。

## 3. 第一版范围

**一个部门，四个用户，一块看板。**

- 组织：人事部（一个 `org_unit`）
- 岗位：人事经理、人事专员（两条 `positions`，由 HR 权威维护，符合决策 5）
- 任职：对应成员各一条 `primary`
-工作项：人事部真实工作项，归属 `position_id`
- 看板：人事部进度看板，老板 / 管理员 / 人事经理 / 人事专员 可见

## 4. 需要新建的东西（按依赖顺序）

1. **迁移 0002：工作项与申报** ✅ **已完成**。文件 `app/workhub/migrations/0002_work_items_reports_and_policy_gaps.sql`，已在临时 PostgreSQL **16.14** 上实测通过，12 项约束逐条验证（`db/verify/0002_constraints.sql`，全部 PASS）
   - `work_items`：`org_unit_id`、`position_id`、`title`、`kind`、`status`、`blocked_reason`、`needs_decision`、时间戳

   - 补齐：主岗唯一性、审批记录表（双签）、`acting` 90 天 CHECK、字段级脱敏
   - 额外加的两条 DB 强制：`blocked` 必须有非空原因；工作项 `org_unit_id` 必须与其 `position_id` 所属部门一致（触发器，否则看板会按部门聚合错）
   - **双签只做到"每人一票、不可重复"**，DB 不强制"凑齐两票"——数据库不知道谁是哪一角色，这条留给应用层读 `approval_records` 判定
2. **看板聚合接口** ✅ **已完成**（未部署前不算数，当前已在服务器跑通）
   - `GET /v1/board/org-units/{org_unit_id}`：阻塞项 → 待决策项 → 按岗位分组，每条带最新申报与 `submitted_via`
   - 写侧：`POST /v1/work-items`、`PATCH /v1/work-items/{id}`、`GET /v1/work-items`
   - 申报：`POST /v1/work-items/{id}/reports`（`submitted_via` 必填、`evidence` 必填）、`GET /v1/work-items/{id}/reports`（历史，含已撤回）、`POST /v1/reports/{id}/retract`
   - **撤回是标记不是删除**，撤回后看板回退到上一条有效申报（已验证）
   - **申报不改工作项状态**：不允许用"追加一条申报"偷偷改写工作项状态，状态变更必须走显式接口并落审计
   - **沉默也要出现在看板上**：`summary` 返回 `never_reported`（有工作项但从没报过）与 `positions_without_holder`（有工作项但岗位无人）。只显示"填报了什么"的看板，恰好藏掉了管理层最需要看到的那一半
   - `latest_report_by_channel` 的 human / agent 之比就是第一版的成绩单
   - 迁移 0003 补发 `workforce.reports` + `submit` 给既有全范围管理员（`bootstrap-admin` 只能跑一次，拿不到后加的动作）

## 5. 三条设计硬规则

1. **工作项挂 `position_id`，不挂 `member_id`。** 这样人走了自动转给继任者（决策 4 已定）。挂人身上就会重演"人走了活没人接"
2. **AI 只能申报进度，不能创建或删除工作项。** 否则 AI 会凭空造工作项，看板变成 AI 的想象。工作项由管理员 / 人事经理在后台维护
3. **`evidence` 必填，看板展示 `submitted_via`。** AI 代笔必须留依据，管理层要能看出这个数是人填的还是 AI 填的

## 6. 两周验收标准（三个都要成立）

1. **人事专员 / 经理第二周仍在填** —— 不是第一周的热情。验证 AI 是否真把填报成本压到接近零
2. **老板实际打开过** —— 查会话与审计记录，不靠嘴说
3. **至少发生一次"因为看到看板而改变的决策"** —— 这条不成立，前面两条都没意义

## 7. 明确不做

- 不做全公司数字孪生
- 不接群聊 / 口头对话 / 本地文件（已降级为可选未来项）
- 不让 AI 搭看板布局（看板结构由管理员配）
- 不做员工自助登录（用 CLI 签发的个人令牌；企微 OAuth 仍卡域名）
- **MCP 不开放除 `submit_progress` 以外的任何写工具**，尤其不得有 `create_position` / `create_assignment` / `grant_permission`
