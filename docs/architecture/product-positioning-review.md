## 2. 核心风险

我们按"岗位是稳定身份、任职有始有终、代理到期自动回收"这套设计建了完整模型，但从未验证过：

- 公司里**真的有**多人兼岗、限期代理、岗位交接这些场景吗？频率多高？
- 管理层现在到底是"看不到进度"，还是"有数据但不可信"？这两个问题的解法完全不同
- 现有工具（企微文档 / 飞书 / Excel / 钉钉）为什么不够？是能力不够，还是没人维护？

如果答案不成立，这套模型的复杂度就是纯成本。**为一个想象中的需求建系统，是自研项目最常见的死法。**

## 3. 三个必须回答的问题

### 问题一：第一个真实痛点是什么（只能选一个）

- [ ] 管理层看不到跨部门进度：谁在做什么、卡在哪、什么时候能完
- [ ] 人走了权限和工作项收不回来：离职/调岗后账号残留、工作项没人接
- [ ] 兼岗和代理没人说得清：谁在替谁、替到什么时候、权限边界在哪
- [ ] 各部门各用各的工具，口径对不上，汇总靠人肉

### 问题二：第一批使用者是谁

- [ ] 管理层（看全局）
- [ ] HR（管人和岗位）
- [ ] 部门负责人（管本部门进度）
- [ ] 普通员工（看自己的活）

**第一批使用者决定第一个版本做什么。** 想同时满足所有人，第一版一定做不出来。

### 问题三：现有工具为什么不解决问题

| 现在用什么 | 卡在哪 |
|---|---|
| | |

如果答案是"有工具但没人维护数据"，那问题不在工具，加一个新系统只会多一个没人维护的系统。

## 4. 三个候选定位

**定位 A：岗位权限中台（当前设计）**
按稳定岗位管权限与责任，兼岗、代理、交接、配置版本全部建模。
- 优点：这是自研唯一能碾压现成工具的地方
- 风险：需要真实的多岗/代理场景支撑；周期长；没人用过之前无法证明价值
- 适合：公司确实存在复杂任职关系，且这个痛点已经造成过实际问题

**定位 B：跨部门进度视图**
不管岗位权限，只做"各部门在做什么、卡在哪"的汇总看板。
- 优点：快，几周能出东西
- 风险：飞书多维表格、Notion、钉钉项目都能做得更好且免维护。**这条路上自研是负收益**
- 适合：确认了痛点就是"看不到"，且现有工具确实做不了（例如要跨系统取数）

**定位 C：单场景切入（招聘 / 某个部门）**
先做一个具体业务场景的协同，验证需求后再决定是否扩展到岗位模型。
- 优点：能最快拿到真实反馈，错了改起来便宜
- 风险：可能被场景绑死，通用性不足
- 适合：需求还没验证清楚时（**当前状态**）

## 9. 后续：AI 化看板提案（2026-10-09）

用户提出转向"AI 原生公司看板"：AI 读规则搭看板、预设模块、各部门定时上传数据。

评估结论：**一个真东西（定时数据接入），两个幻觉（AI 搭看板、预设模块）**。但提案里"给 AI 建规则"这个直觉是对的——只是规则的内容应是组织语义（岗位/任职/权限），不是布局。因此这不是推翻定位 A，而是给定位 A 加一层 AI 接口。

**第二轮更正（同日）**：用户澄清 AI agent 是**用户自己带的**，我们不提供、不托管。我们只提供 **MCP 服务 + Skill 规则文档**；定时上报也不是我们抓取，而是用户按业务需要让自己的 AI 设定时任务，Skill 里告知 AI 有这个能力，AI 再告诉用户。

更正后定位收敛为：**OAMS = 公司组织语义的 MCP 服务**。撤回第一轮"别做通用 agent"的判断（建立在错误假设上）。新增关键原则：**Skill 是提示词，不是执行保证，所有安全必须在 MCP 服务端强制**。行级过滤与字段脱敏从"以后再说"上升为"MCP 开放第一天的阻塞项"。

后续决定：认证统一由独立账号中心提供。当前 MCP 继续使用受控 bearer token，未来由账号中心的稳定主体映射替代临时签发流程。

**第三轮（同日）**：用户确认四项——①**不能无头**，最终目标是管理层看的**公司数字孪生看板** ②首批 MCP 客户端为 WorkBuddy、Codex 等 ③核心场景是把散落在**群聊、口头对话、员工本地电脑**里的进度借 AI 梳理接入 ④定时上报是 **AI 帮用户自动上报**，不是用户自己填。

判断：**方向对，起点错**。第 3 点是真痛点且无人做（飞书/Notion 处理不了"差不多快了"这类非结构化信息），但要从**最不可信**的源建"数字孪生"，顺序反了。

最大风险不是技术，是信任：①「明的暗的都可视化」在员工视角就是监控，会导致不配合 + 报假数据，结果是看板漂亮、数据是垃圾 ②不可信源被 AI 结构化后更危险——没有数据时管理层知道自己不知道，有假数据时他以为自己知道 ③AI 读本地文件/群聊涉及个人信息处理，需授权合规。

强制设计：**每个数据点带来源与置信度，L1 权威事实源 / L2 人工填报 / L3 AI 推断三层不可混同显示**。

建议**先做 L1**（接商品中心等已有可信源，做一块真看板给管理层看），验证"管理层真的会看"之后再补 MCP、加 L3。

**已暴露的冲突**：「数字孪生」与已确认决策 3（管理层只看部门级汇总、不看个人明细）直接冲突，必须先澄清管理层能看到多细。
